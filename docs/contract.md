### onepipeline-ui contract

Rust (axum) server wrapping the onepipeline SDK. Endpoints preserved so the copied frontend re-points with minimal change:

```
GET /healthz
GET /api/v2/runs                      # list w/ session attribution
GET /api/v2/runs/{run}                ?include_conversations=bool&filter=SPEC
GET /api/v2/runs/{run}/timeline       ?scope=run|node&node=ID&filter=SPEC
GET /api/v2/runs/{run}/conversations/{id}
GET /api/v2/runs/{run}/artifacts/{id}
GET /api/v2/events                    # SSE; fresh snapshot per connection; ?filter=SPEC
```

`/healthz` is the one response that is not enveloped — liveness must answer without reading run storage, so it has no schema version to read one from — and it carries two fields: `status`, whose only value is `ok`, and `onepipeline_version`, the `onepipeline` release this binary links, read from that crate's own `VERSION` rather than restated here and served as a validated `MAJOR.MINOR.PATCH` — a body naming a release nobody could have published is refused at the parse rather than compared against. A host that pins the engine writing a run store and separately pins this reader of it has nothing else to prove the two are the same release, so the reader says which one it is rather than leaving it assumed.

Payloads keep the telemetry schema-version discipline and serve schema 14 including `dispatch_id` — schema 10 was where `dispatch_id` landed, and 11 is that discipline exercised: an unmeasured timing is served `null` rather than `0`, so a lane nothing measured can no longer read as a measured zero. Anything the API computes that is presentation-worthy lands in the onepipeline SDK/CLI first: the agent reading the CLI must have the same or better visibility than the human in the UI.

Schema 12 answers, per node in flight, whether the run has a turn it can address for it — the precondition a planner needs before choosing between correcting a node and cancelling it. `node_control` carries one entry for every node recorded as `running` and for no other, and each entry is `{addressable, member?, reason?}`, with `reason` present exactly when `addressable` is false. A node whose turn this run cannot address reads as `addressable: false` carrying the reason — never as an error and never as an absent value — and where an interrupt has already been attempted the reason is the producing library's own words for what it found.

`addressable` means **this run has a turn it can address for that node** — the engine's own precondition for delivering a note into a running turn — read from whether a member is in a turn and from the outcome of every interrupt already attempted, which is published for every attempt whether or not it landed. It is not a claim that the harness will accept a redirection. No published component exposes an authoritative *current-turn* control state outside the process running the turn: onejudge reports `control` only on the finished run, the live provider accessor is in-process only, `oneagentgraph`'s spawn-time record is provisional for every member whatever its harness, and the control protocol's only verb is `interrupt`, which costs the turn. A previous dispatch's report is not a substitute and is never read as one — `provider.control` is asked for per run and reset for the next. `src/AGENTS.md` records each closed route and the upstream change that opens one.

**Schema 13 is the removal of rounds.** Execution in the onepipeline SDK is continuous and dependency-driven: a node — and each step within a lifecycle node — dispatches the moment its dependencies settle `done`, nothing batches them, and the envelope's `round` label is deprecated and stamped by nothing. So the payload's `rounds` array is replaced by one **`graph`** object describing the run's whole state, and no `round` survives anywhere in a response. A client reading 12 must not read a 13 payload: the array it indexed is gone, not renamed. `graph` is `{run_id, plan, node_states, node_status, node_gated_by, node_control, node_results, decisions, attestations, result, last_seq}` — one desired graph with every committed live edit applied, and one recorded `result`, which the SDK rewrites whenever a driver closes out.

**Schema 14 is the transcript a dispatch really had.** A conversation turn is assembled from the **stored onejudge report** the settling member left, and not from journal envelopes alone — the journal records that a session reported and what tools it called, which is almost none of what a transcript is. A settlement carries no `session` label and needs none: a session id is `{stream}.{member}`, so the settlement a transcript belongs to is the one whose stream and member spell it, and the run's copy of its report is located the one way this contract allows, through `RunPaths::report_for(STREAM, SEQ)`. A turn is joined to what the report says about it by the producer's own 1-based turn number, which `turn-started` carries and which is the counter the report shares between `telemetry.sessions` and `telemetry.attribution`.

Under 14 the fields `DagConversationTurn` has always declared are filled: **`user`** is the prompt the simulated user gave and is never the dispatch's persona name — who was asked is not what they were asked; **`assistant`** is the reply that turn wrote, and `null` for a turn whose report recorded none; a **tool event** carries the observation it returned wherever the report holds one, and `output: null` where the trace exposed none; **`usage`** and **`durationMs`** are what *that turn's own invocation* spent and took, read off the candidate that `ran` in the turn's `role: agent` attribution — the report's top-level `usage` is the whole dispatch's total over both sides, and serving it per turn would repeat one total on every one; and **`startedAt`/`finishedAt`** are that turn's agent-side `telemetry.sessions` bounds where the report holds them and `null` where it does not. **No figure recorded against the judge is ever served on an agent turn** — not a bound, not an elapsed time, not a usage count. `role` in `telemetry.sessions` says which *side ran* and `role` in a transcript message says *who wrote it*; they are two vocabularies that share no word and are never read as one. A session whose member has not settled, whose report the run does not hold, or whose document cannot be read as a report is served exactly as the journal relayed it rather than emptied.

Under 14 a settled dispatch also serves **the judge's own conversation and the lane it is reachable through**, and neither schema version moves for it: it is a conversation and a span, not a field or a vocabulary member. Nothing relays a judge session and no producer change can — a plan node dispatches one graph member and the judge runs *inside* onejudge, so there is no `session` label for the transcript listing to group on and no relayed record for a timeline span to be bracketed by. The stored report is the whole of what any run holds about that side, and it holds it only once the member settles, which is why a dispatch still running serves one lane. Its id is the worker session's with `.judge` after it, so the conversation route resolves it through the same lookup as any other; it is attributed `agentRole: judge` and `transportRole: judge`, and it names the dispatch it supervised as its `parentConversationId`. One turn per `role: judge` `telemetry.sessions` row — the only per-turn bounds a report holds for that side — carrying that row's start and end, and the model, elapsed time and usage of the candidate that `ran` in its `role: judge` attribution, with a figure the provider never reported served absent rather than as a zero. **No text is served against a judge turn**: the report keys none to one, judge turns outnumber the agent's, and nothing records which turn wrote which instruction — the judge's authored prose reaches the wire already, as each agent turn's `user` message. One closing turn carries what the report keys to the *dispatch* instead: every criterion it judged, the verdict and reason it returned for each, its closing assessment, why it completed and whether it stopped early — served whole, because the bound this API puts on an artifact's bytes is not one it puts on a report-backed read — and with no bounds and no usage, because the report records none for it. The lane beside it is served as a **sibling of the dispatch span**, at the same node, step and `dispatch_id`, drawn over those same rows: it opens at the earliest of their starts and closes at the latest observed finish, and a row whose end was never observed leaves it open under the rule every unclosed span here is served by.

14 also removes the one reading that measured nothing. A usage record on this wire is `onejudge::Usage` — `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `cost_usd` — because `oneagentgraph` relays a settling member's usage copied verbatim out of that report; the six keys this API read one by were spelled the way a declared-but-unwritten type spells them, so every served cost and token count was `null`. There is no `duration` among them and there never was: a turn's elapsed time is its attribution candidate's `duration_ms`, served on the turn it belongs to as `durationMs`. The per-party `*_model_ms` lanes a run's `timing` carries, their fractions, and `node_work_ms` are therefore served **absent**, with the presence flags beside them saying so — nothing in this stack reports how long a party spent inside a model, and an invocation's wall clock is neither a model's clock nor a party's. A tool call's own interval is unmeasured on the same terms.

`decisions` is what replaces a round's own account of why a run is not moving. The only thing that pauses anything is a **decision point**, and it pauses only the subtree that depends on it — a ready `kind: human` node's attestation, or a blocking surface nobody has answered — while independent branches proceed. Each entry is `{id, kind, unblocks}`, mirroring the SDK's own `decision-pending`, and it is absent from the list again once `decision-cleared` releases the subtree. `phase` names a continuous phase — `starting`, `dispatching`, `deciding`, `surfacing`, `waiting`, `settled`, `finished` — rather than a position in a batch, and `node-ready` is the kind that reports a node became eligible to dispatch. Plan schema 2 retired `done_when`, so no plan task carries one: a node's bar is the `## Acceptance criteria` section of its own task prose, which is what the judge is handed.

Timeline schema 4 carries the redirection itself. An event produced by a `turn-interrupted` or by an `edit-committed` that added context to a node carries `redirection` — `{delivered, member?, input_bytes?, reason?, delivery?, node_id?}` — so a turn whose behaviour changed mid-flight shows the moment the planner changed it, and whether the note went into the running turn (`live`) or onto the node's next dispatch (`deferred`). An `edit-committed` additionally carries the `author` that submitted it, `planner` or `monitor`: the run enforces a per-author op allowlist, so an observer's self-applied fix and the planner's own decision are two different facts about one graph.

**Timeline schema 5 is continuous too.** The run itself is the single root span (`kind: "run"`), not one span per round; no span or event carries a `round`; and every span id is keyed by what it identifies — `run.RUN`, `node.ID`, `dispatch.SESSION`, `publication.ID`, `verification.ID.ARTIFACT`, `rollup.ID.…`, `human-wait.ID` — rather than by a round number. A node has one span however many times it was dispatched: the SDK re-asks a dispatch that produced nothing and records each attempt as its own `node-dispatched`, and every attempt is the same node's same work.

**Timeline schema 6 says what one lane was doing, and when.** Under 5 a node's own window was every span's window: each `dispatch` span carried the node's first dispatch and last settlement, and each `scope=run` `rollup` the same pair — so a node the engine re-asked served one span per session over one identical interval, and a drafting turn that took a minute was drawn across the hours of work it drafted for. A session is now bounded by **the attempt that ran it**. It opens at that attempt's `node-dispatched` — the latest at or before the session appeared — and it closes at the earliest of the next `node-dispatched`, the `node-settled` that followed it, the `session-closed` that took its worktree away, and the `member-settled` or `member-died` that ended the session itself, the last of these joined to it by its `{stream}.{member}` id. Nothing may close it before the last thing it said, and where none of those records exists it is served with a null `ended_at`, which is a session still running. **Every session of one attempt opens at that attempt's dispatch**, including one the attempt reached only after another had finished: an attempt is the unit a session is bracketed by, the run records no boundary between the members inside one, and a session is never opened from its own first word. So a node dispatched three times serves three spans over three different intervals, while a lifecycle node dispatched once serves its worker and its drafting turn from the same moment and closes each where the run said that member was over. A category's rollup covers the sessions in it rather than the node they ran under.

A **`publication`** opens at the first record that is publication work rather than at the worktree the dispatch was cut into: `onevcs` cuts a worktree when the node is dispatched, so under 5 the span covered the work being published rather than the publishing, and a node that never published was drawn publishing to the end of everything it recorded. A node that did no publication work serves no publication span at all, and `session-closed` now closes one — ranked behind a merge, a conflict and an opened change, because it says only that nothing more can happen on that branch. A publication the run ruled on carries its `status`; one whose worktree simply went away carries none.

A span's **`agent_role`** is read from the `member` the run recorded for the session, falling back to the persona only where no member was stamped. A persona is a style a host invented — `engineer`, `docs-writer` — so reading a role off one dropped every session a host had not named after a role, and a run-scope reading showed an empty `Worker` lane beside the one drafting turn whose persona happened to be the word `pr-author`. The `monitor` member is served as `orchestrator`: it is the same lane, and `agentRoleSchema` is a closed vocabulary a client switches on exhaustively, so no member joins it or `timelineSpanKindSchema` under 6. The two rules a client already depended on are unchanged: a span the run never closed is served with a null `ended_at` and is never given an invented one, and a span nothing measured is served absent rather than as a measured zero.

**An artifact is served as `{id, kind, content, truncated}`, and where its bytes are read from is decided by what the producing library said it stored.** The body is the end of the file rather than all of it — a producer promises no size, and a read surface that streams an unbounded one into a browser can be made to exhaust its own memory — so `truncated` says whether anything was left off the front. `kind` is the wire's closed reference vocabulary (`conversation`, `gate_log`, `worker_report`, `oneharness_session`, `pr`), read from the producer's own word for the artifact.

A **`worker_report`** — the report `oneagentgraph` records on every `member-settled`, which is the judge's ruling against each acceptance criterion, the follow-ups the worker surfaced, and why it stopped — is the one kind the run holds a copy of. `onepipeline` copies it into the run's own storage as the settlement is ingested, and **retention and resolution are one published promise**: this API resolves it by calling that SDK's `RunPaths::report_for(STREAM, SEQ)` on the envelope the artifact was recorded on, and never by restating that name or the sanitiser behind it. The artifact id names the stream but **not** the seq, which is why the envelope rather than the id is what locates the file. A settlement whose copy the run does not hold — `retain` refuses a report that is a symlink, is not a plain file, is misnamed, or is past its size bound — is `404 artifact_not_found`, never an empty body.

An **`oneharness_session`** is the conversation one oneharness invocation actually had, and it is the one kind whose bytes are **not under the run at all**. Nothing copies a session into a run: `oneagentgraph` publishes a pointer — `history_dir`, `history_project`, `history_session` and the `history_id` that is also the artifact's id — and the transcript stays in the oneharness history store on the host. So this API resolves one by **linking the published `oneharness-core` crate**: `io::history::resolve_dir` for a record that named no store, then `io::history::find_session_path` and `io::history::read_session_display`, selecting the record whose history id is the artifact's and serving it as pretty JSON, bounded exactly as a log is. Never `io::history::find_record_by_id`, which reconciles the store's index under an exclusive `flock` and rewrites it — a read surface must not stand in the way of the single writer the engine runs — and never by spawning the `oneharness` CLI. There is no flag and no config key here for that store: the record names it, and the fallback is the same default every oneharness process on the host resolves, because a second source for that path is how a reader and a writer come to disagree about where the transcripts are. **`history_project` and `history_session` come off a record, which is external input exactly as a URL is**, and each is checked as a bare name before anything joins it; a value that climbs, carries a separator, is absolute, or names a dot file is `404 artifact_not_found` rather than a file opened somewhere else on the host. So is a history id the store does not hold.

Every other kind is a log the producing library stored beside the run, under its own id.

#### Read-time filtering

`?filter=` on the run-detail, timeline and event-stream routes selects which events a response carries. It takes either a **named profile** or an **inline spec**, and it is resolved against the run being read.

Two profiles are defined for every run, whatever it was launched with. **`planner`** is the decisions-level view: onepipeline's own event vocabulary is a closed set and it is exactly the decision vocabulary, so the profile is `include: [{source: "pipeline"}]`. **`monitor`** is detailed activity — the whole merged stream, all three sources — which is what the monitor persona's own contract says it reads; it narrows nothing, and is named rather than derived so that the two settings a viewer switches between are two profiles rather than a profile and an absence. A run's launch config may define further names: a retained `onepipeline start --set filters.NAME=SPEC` override, which the launch record keeps verbatim, defines profile `NAME` for that run alone and may not shadow a built-in one. A name no profile answers to is `404 unknown_filter_profile`, and the message lists the names that run does have.

The inline form is the stack's shared grammar, duplicated here per repository exactly as the envelope is: `{"include": [MATCHER, …], "exclude": [MATCHER, …]}`, where a matcher may name `source` (exact), `kind` (a glob over the wire string, where `*` stands for any run of characters including none), and the reserved label keys `run_id`, `node`, `step`, `member`, `persona` (exact). Every field a matcher names must hold; a field it does not name is not consulted; a label the envelope never stamped matches nothing. **`exclude` wins**, and an absent or empty `include` admits everything. There is no `round` matcher — there are no rounds. A spec is validated at the trust boundary before any run is read: a matcher naming no field at all, or one whose field is empty, is `422 invalid_request` naming which list it is in, where, and what it says.

**Filtering shapes responses and never run state.** The API is read-only, and a filter narrows only the events a payload carries: every node status, settlement, decision, count and timing is folded from the whole journal whatever the filter said, so a reader narrowing their attention is shown the same graph in the same states as one who asked for everything. On the event stream — which invalidates rather than restating state — a filter decides which movements are worth announcing, so a run whose only new records the filter excludes does not wake that subscriber.

The browser view carries this as one affordance: a **Decisions / Detailed activity** switch in the toolbar, held in the query string as `?detail=` alongside every other selection, so a narrowed reading is bookmarkable and survives a back button. It maps to the `planner` and `monitor` profiles, which is the same distinction those two get on the CLI.
