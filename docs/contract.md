### onepipeline-ui contract

Rust (axum) server wrapping the onepipeline SDK. Endpoints preserved so the copied frontend re-points with minimal change:

```
GET /healthz
GET /api/v2/runs                      ?limit=N&cursor=RUN&include_settled=bool&select=RUN,RUN
GET /api/v2/runs/{run}                ?include_conversations=bool&filter=SPEC
GET /api/v2/runs/{run}/timeline       ?scope=run|node&node=ID&filter=SPEC
GET /api/v2/runs/{run}/conversations/{id}
GET /api/v2/runs/{run}/artifacts/{id}
GET /api/v2/events                    # SSE; ?subscription=ID&after=EVENT-ID: a subscription's changes; else fresh snapshot per connection; ?filter=SPEC
GET /api/v2/projects                  # verbs::runs, grouped: newest activity first
GET /api/v2/projects/{project}        # one group; 404 project_not_found
GET /api/v2/runs/{run}/channel        # verbs::channel: the queue, consuming nothing
POST /api/v2/runs/{run}/channel/next  ?filter=SPEC — verbs::next: claims a surface
POST /api/v2/runs/{run}/channel/reply ?correlation=C — body = the envelope bytes, verbatim
POST /api/v2/runs/{run}/channel/surface  {kind, message} — verbs::surface
POST /api/v2/runs/{run}/attest        {reference} — verbs::attest
POST /api/v2/runs/{run}/stop          {force?: false} — verbs::stop as the acting session
POST /api/v2/shutdown                 {scope: "host", grace?: seconds, force?: false} — verbs::shutdown(Host)
GET /api/v2/unwatched                 # verbs::Unwatched::within for the acting session, under the server's ONEPIPELINE_WAKE_BUDGET
GET /api/v2/host                      # verbs::host
GET /api/v2/runs/{run}/status         # verbs::status(Some(run))
GET /api/v2/runs/{run}/results        # verbs::results
GET /api/v2/goals                     # verbs::goals(None)
GET /api/v2/runs/{run}/goals          # verbs::goals(Some(run))
GET /api/v2/runs/{run}/transcript     ?node=ID — verbs::transcript
GET /api/v2/runs/{run}/telemetry      # verbs::telemetry(Some(run))
GET /api/v2/runs/{run}/agents         # verbs::agents(Run): every oneharness session the run launched
GET /api/v2/runs/{run}/nodes/{node}/agents  # verbs::agents(Node): the sessions one node's dispatches wrote
GET /api/v2/projects/{project}/agents # verbs::project_agents: the union over the project's runs
POST /api/v2/subscriptions            {view, replaces?, resume?} — a tab's subscription and its initial snapshot; 201
DELETE /api/v2/subscriptions/{subscription}  # retire it: its reads and its stream end; 204, idempotent
```

The first seven are the read surface the browser view was copied against, and the rest are **the post-launch CLI, wrapped**: every route after `/api/v2/events` is a thin call into `onepipeline::verbs` — the SDK surface that the `onepipeline` binary is itself argument parsing over — and this API never runs that binary, never re-implements a verb, and never opens a run's files by a path of its own where the SDK has a call. The server acts as **one launching session** (`--session ID`, else `ONEPIPELINE_LAUNCHER_SESSION`, else unattributed), and that is the whole of its identity: it is passed to `verbs::stop`, `verbs::shutdown`, `verbs::Unwatched::within` and `verbs::runs`,. It never rewrites an envelope: `POST .../channel/reply` forwards the request body to `verbs::reply` byte for byte, an omitted author is `planner` by the engine's own contract, and any other author the body names is judged by the run's launch configuration inside the SDK.

**Content encoding.** A request whose `Accept-Encoding` takes `gzip` (named with a non-zero weight, or covered by `*` and not refused by name; a coding whose weight is not an RFC 9110 `qvalue` is no offer) is answered `Content-Encoding: gzip`, and any other request is answered with the body unencoded. Either way the body is the same document. Every response carries `Vary: accept-encoding`. A `text/event-stream` body is flushed after every frame and every heartbeat, so an encoded stream delivers each frame as soon as an unencoded one would, and what has arrived always decodes up to the last whole frame. A body known to be empty, such as a `204`'s, is never encoded.

#### The browser view, served beside the API

`onepipeline-api serve --runs-root DIR --bind HOST:PORT` serves the routes above and nothing else: a path none of them owns is the error contract's `404 no_such_route`. With **`--ui`** the same server, on the same one address, also serves the browser view — the DAG Observatory bundle `apps/dag-ui` builds and the `onepipeline-ui` npm package publishes — and the split is by path, exactly as the same-origin proxy a consumer used to write split it: `/healthz` and everything under `/api` are the API's, answered as they are without the flag, and every other path is the view's. A path the bundle has a file at is answered with that file's bytes and content type; every other path is answered with the bundle's `index.html`, so a deep link the app's router owns opens rather than 404s. A request under the API's prefixes is never answered by the bundle — a route the API does not have is still `no_such_route`, as JSON — and a request for the bundle is never answered by the API. The flag is off by default, so a caller that asked for the read API alone gets exactly what it always got.

The bundle `--ui` serves is **embedded in the binary at build time**: `build.rs` compiles the built `apps/dag-ui/dist` into the one binary the crate, the PyPI wheels and the npm launcher all wrap, so a host that installed only that binary opens the view of the same release with no npm package beside it — the pairing `release-targets.toml` already declares one release makes. Every prebuilt distribution is built with the `bundled-ui` feature, under which a missing bundle is a build error; a build without the feature — a `cargo install` from crates.io, whose tarball carries the view's sources and not its build — embeds the bundle when it has been built and otherwise refuses `--ui` naming what is missing, exit `70`, never serving an empty page. **`--ui-dist DIR`** serves the bundle at `DIR` in place of the embedded one, read per request: it is how the view is developed against a real runs root, and the only way to serve a bundle of another release. It qualifies `--ui` and is a usage error without it, as is a directory holding no `index.html`.

#### Projects, and what a run-list row now carries

`GET /api/v2/projects` serves the SDK's own grouping, `verbs::runs`, in its own order: `projects` is the groups **newest activity first** — by the group's own `last_write_at`, then by project id — and each group's `runs` are that project's runs newest first, exactly as the flat listing orders them. A run whose summary recorded no project is in the **`(no project)` group**, an ordinary group whose `project` is `null`, ordered by its own recency and never hidden or last by rule. Each group is `{project, name, last_write_at, runs}` — the qualified onetaskgraph project id or `null`, the plan's name off the newest run that recorded one or `null`, the newest write in the group in milliseconds since the epoch or `null`, and the rows — and each row is the **same row `GET /api/v2/runs` serves**, so a row carries the run's settlement (`state`, `phase`), its `node_counts`, its `liveness`, its `unread_surfaces` and its last write (`last_progress_at`). A root the reader refused is named on `unreadable`, on the terms the run list names one. `GET /api/v2/projects/{project}` is one group, and a project id no group carries is `404 project_not_found`; the no-project group is not addressable by id, because it has none.

`{project}` is a validated identifier: `<source>:<native>`, where the source is one of onetaskgraph's under `^[a-z0-9][a-z0-9-]*$` and the native id is a non-empty bare token carrying no separator — the same characters a run id may — and it is **path-encoded on the wire**, so a client sends `local-md%3Aproject-grouping` and the route reads the id back through its parser before anything is compared against it.

**Schema 18 is what a run-list row says about where a run belongs and whether anything is waiting on it.** Four fields, all additive: **`project`**, the qualified project id the run was launched with, absent for a run whose summary recorded none; **`project_name`**, the plan's name as the run recorded it, absent where none was; **`liveness`**, the SDK's own word for how the run is being driven — `ACTIVE`, `DRIVER DEAD`, `PARKED` or `UNDRIVEN`, read through `views::liveness_of` over the bounded summary, which is the reading `onepipeline runs` prints — served whether or not the run has settled, where `state` folds the settled case in; and **`unread_surfaces`**, how many surfaces the run has raised that nobody has read, counted off the run's channel exactly as the CLI's `runs` line counts them. Every field 17 served is served with the same meaning and the same value, so a client written against 17 reads an 18 payload unchanged; the version moves because a client that has never seen `liveness` reads a run holding an unanswered question as one nothing is happening to, and a client that has never seen `project` cannot group the list the way the CLI does. The event stream's invalidation frames carry the same fact: a `run.changed` names the `project` the run that moved belongs to beside its `run_id`, where its summary records one, so a client refreshing by group refreshes the group that moved.

#### Subscriptions: pushed changes for what a tab shows

**Schema 25 is pushed changes.** A tab holds **one subscription**: the sidebar and at most one visible run view. Creating it answers the state the tab shows at one publication boundary; its stream then carries only what changed after that boundary — a trimmed sidebar row per run that moved, and a patch of the visible payload — and never a whole payload during a healthy stream, however large the patch. Moving to another view replaces the subscription and retires the old one, so a view the tab no longer shows is neither read nor pushed. A subscription creates read state only; it never owns, claims or acts on a run. Every field 24 served is served with the same meaning and the same value; the version moves because a client written against 24 re-reads whole payloads on every change, and has never seen `run.live_activity`.

**`POST /api/v2/subscriptions`** takes a JSON body with no member beside these: `{view, replaces?, resume?}`. `view` is one of `{type: "sidebar"}`, `{type: "detail", run_id, filter?}`, `{type: "timeline", run_id, scope: "run", filter?}`, `{type: "timeline", run_id, scope: "node", node, filter?}` and `{type: "channel", run_id}`; `filter` is the `?filter=` grammar and default below. The Graph view subscribes `detail`, Overall `timeline` at run scope, a node's timeline `timeline` at node scope, and Channel `channel`; the Host page and a page with no run open subscribe `sidebar`, and the Host page's own reads — `GET /api/v2/host`, `GET /api/v2/unwatched`, the listing — are taken when it opens and on its refresh control and never on a change. `replaces` names the subscription this one replaces, retired atomically once the replacement is made; one that is missing or expired is harmless. `resume` is the last event id applied, sent only when recreating a subscription the server no longer has, and is exclusive with `replaces`. A malformed body, view, filter, id, or a node scope naming no node (or a run scope naming one) is `400 invalid_subscription`; a run that is not under the root is `404 run_not_found` and a node the run does not carry `404 node_not_found`, both refused before anything is opened. The answer is `201 {subscription, view, initial}`: `subscription` an opaque UUID, `view` the view as normalized (the filter in its normalized spelling, omitted where none was asked for), and `initial` either `{type: "snapshot", snapshot}` for a fresh subscription or a **reset frame** (below) for one created with `resume`. **`DELETE /api/v2/subscriptions/{subscription}`** retires one — its reads and its stream end — and answers `204` whether or not it was still held.

**A snapshot** is `{id, sidebar, visible}`. `id` is an **event id**, `<epoch UUID>:<unsigned decimal sequence>` written one way only (lowercase hyphenated UUID; no sign, no leading zero); the epoch is chosen when the server starts and the sequence increases across every snapshot and frame the process issues, with gaps, because other subscriptions take numbers too. `sidebar` is one **sidebar row** per run under the root, and a row carries exactly the fields the sidebar renders and no other: **`id`** (the run id), **`name`** (its displayed name: the run id), **`group`** (`{project, name}` — the effective qualified project id and the recorded plan name, falling back to the project's native id as the engine names a group — or `null` for a run with no project), **`kind`** (the effective `labels.kind`, or `null`), **`state`** (the run-list row's `state` vocabulary, unchanged), **`nodes`** (`{total, done, failed, running}`, non-negative counts from the run's projection), **`updated_at`** (its last recorded activity, RFC 3339 UTC, never the time of the read) and, only where the run recorded one, **`started_at`** (its launch time). No session id, liveness or run detail rides a row. The browser orders and groups projects from these rows: a project's runs by launch time, newest first, undated launches after dated ones by last activity — the ordering the navigation section below states. `visible` is `{type: "sidebar"}`, `{type: "detail", run_id, detail}`, `{type: "timeline", run_id, scope: "run", detail, timeline}`, `{type: "timeline", run_id, scope: "node", node, detail, timeline}` or `{type: "channel", run_id, detail, channel}`, where `detail` is exactly the envelope `GET /api/v2/runs/{run}?include_conversations=false&filter=` serves, `timeline` exactly `GET /api/v2/runs/{run}/timeline?scope=…&node=…&filter=`'s, and `channel` exactly `GET /api/v2/runs/{run}/channel`'s. A timeline or channel view carries the detail beside it for the header and graph state already on screen, and that detail subscribes nothing else. The detail's `run` gains **`live_activity`** under schema 25: what each node was last seen doing from inside a turn, one entry `{event_id, node, step?, at, kind, name, detail, events}` per node, oldest first — the run's `turn-activity` records over the whole journal, which a filter does not shape — so the header's activity line is patched with the rest of the detail.

**The stream** is `GET /api/v2/events?subscription=ID&after=EVENT-ID`, `text/event-stream`; a non-empty `Last-Event-ID` header takes precedence over `after`, and a first connection names the snapshot's id. Every data frame's SSE `id` is its `data.id` and its SSE `event` its `data.type`; comments are heartbeats and carry no state. Every frame carries `{id, base, subscription, type}` — `base` is the id of the frame before it on this subscription, the snapshot's id for the first — and one of: **`run.changed`** `{row}`, one complete trimmed row upserted; **`run.removed`** `{run_id}`, the row deleted (a removed visible run leaves the visible state unavailable, and no other view is subscribed in its place); **`detail.patch`** `{run_id, ops}`; **`timeline.patch`** `{run_id, scope: "run", ops}` or `{run_id, scope: "node", node, ops}`; **`channel.patch`** `{run_id, ops}`; and **`reset`** `{reason, snapshot}`. A patch targets this subscription's corresponding payload, whole envelope from its root. **`ops`** apply in order and atomically, each exactly one of `{p, v}` (set the object member at path `p`, or replace an existing array element), `{p, a}` (append the array `a` to the array at `p`) and `{p, d: true}` (delete the object member at `p`); a path is object keys and non-negative array indices. The root is never replaced or deleted — that would be a whole snapshot in disguise — and `p: []` names it only for an append to a root that is an array; every parent must exist; a deletion never shifts indices, so an array that lost or reordered elements is replaced with `v` at its own path. An operation outside these rules is a protocol error: the client stops applying and says so, never replaces its state or claims success.

**Resume.** Each subscription retains its latest **4,096** emitted frames, and the cursor before the oldest of them. A stream replays, in order, every retained frame strictly after the cursor it names, then sends new frames as they are made; the client ignores a frame it has already applied, advances its cursor only after applying one, and does not apply a frame whose `base` is not its applied cursor — it reconnects from that cursor instead, which is what keeps a replayed append from landing twice. A disconnected subscription keeps recording its changes for at most **120 seconds** under the same bound, and a connected stream never expires however quiet it is; a replacement or a `DELETE` retires one at once. On the same live subscription, a cursor older than the retained boundary is answered with a reset of reason **`stale-cursor`**, one this subscription never issued with **`unknown-cursor`**, and one naming another epoch with **`server-restarted`**: a reset's `base` echoes the refused cursor, its `snapshot.id` equals its own `id`, it replaces the sidebar and the visible state once, and patches resume after it. **It is the only whole re-send a stream makes.** A stream asked for a subscription the server cannot serve is `410 {code: "subscription-unavailable", reason}` with `reason` `expired`, `server-restarted` (a cursor naming another epoch) or `unknown`; the client then recreates the same view with `resume` set to its last applied id, and is answered with a reset — `server-restarted` for another epoch, otherwise `unknown-cursor`, because the subscription is gone — naming the new subscription. A malformed cursor is `400 invalid_subscription`, never a guessed baseline. Cursors are scoped to their exact subscription and are never reused across a replacement.

**No restated snapshot.** A subscription's stream opens with **no** run-list snapshot: the tab already holds the rows its `POST` answered, and a reconnect resumes after the last frame it received. The invalidation stream without `?subscription=` is unchanged — every connection opens with a fresh run-list snapshot, and a `run_id`-scoped one with a snapshot of that run alone — and no page of the browser view reads it any more.

**What the server reads for it.** One poller serves every subscription, once per poll interval (`--poll-interval-ms`, 500 ms by default). For the sidebar it looks at each run's journal, bounded summary, label overlay and result metadata, and reads a run's bounded summary only when one of them moved, and then at most once every **10 polls** for that run — so a run's row is pushed at most that often however often it moves, to what it then holds. The summary is the one the engine's own writer keeps current as it appends, which the engine folds again from the journal only where a writer left it behind. Each **subscribed** run is held open as one long-lived `RunView`, kept current with `RunView::refresh`: an `Appended { first }` folds only the appended records, and the detail and timeline patches are built from them — the shares of the payload whose owners those records name, rebuilt over their own records — while a `Reread` rebuilds the payloads whole and is still sent as their structural difference. A run no subscription shows is never opened, and two tabs on one view share one reading. The SDK's whole-journal telemetry fold, the one part of a detail no suffix can update, is folded again once something moved on the first tick at least 10 seconds after the last fold that carries no change — and on a run that never goes quiet, once it is 20 seconds behind — so no change waits on it.

#### Acting on a run

Every mutation is the SDK's own verb and answers with the SDK's own result, projected: a refusal the engine makes is served as the engine's own words, never restated. `verbs::Error::NotOwned` is **`409 not_owner`**, and its message names the owner as the engine names it to a caller that is not it; `Error::Refused` and `Error::Invalid` — a malformed envelope, an op the author is not granted, a reference nothing is waiting on, a run something is still driving, a message with nothing in it — are **`422 refused`** carrying the engine's text; `Error::NothingDriving` is `409 nothing_driving`, `Error::Locked` is `409 locked`, and a ledger or sibling failure is `500 engine_error`. A run that is not under the root is `404 run_not_found` on every route.

- **`POST /api/v2/runs/{run}/channel/next`** is the channel's only consumer: it claims the next surface, journals `planner-surfaced`, and restarts the check-in clocks the run's observer graph declares resettable, exactly as `onepipeline next` does. `?filter=` shapes the `events` it answers with — a profile or an inline spec, as the CLI's `--filter` — and shapes nothing else: a blocking surface reaches its planner under the narrowest profile. The payload is `verbs::Next`: `{status, surface, events}`, where `status` is `surface`, `running` or `finished`.
- **`GET /api/v2/runs/{run}/channel`** is `verbs::channel`: `{surfaces, waiting, held, replies, commands, outcomes}` — every surface raised, the ones nobody has read, whatever the pending slot holds, every reply written, the edit envelopes the reconciler has not claimed, and its answers to the ones it has. A reading, never a record: it consumes, claims and answers nothing.
- **`POST /api/v2/runs/{run}/channel/reply`** hands the request body to `verbs::reply` as the envelope's bytes, verbatim, with `?correlation=C` parsed through `onemessagebus::Correlation`'s own parser and refused as `422 invalid_correlation` where it is not one. The body is not read here: a malformed envelope is the engine's refusal, in the engine's words, and an author the body names is granted or refused by the run's launch configuration inside the SDK. The payload is the receipt entry 64 of the engine's divergence record states — `{reply, state, verdict?, commands?}` — under `receipt`, with the engine's `advice` beside it as an array of sentences, so a queued edit tells the manager what has to drive the run for it to take effect. That includes the engine's graph-override edits, `{"op":"set-node-sets","id":…,"sets":[…]}` and `{"op":"set-run-node-sets","sets":[…]}` at reply-envelope version 3: each replaces its whole ordered list, `[]` included, and whether one is accepted — an unknown or settled node, an entry the node-scope graph cannot apply — is the engine's ruling, in its words, with a refused one changing neither list. Nothing here re-reads or re-encodes them, and the engine driving the run replays accepted edits on its next dispatch.
- **`POST /api/v2/runs/{run}/channel/surface`** takes `{kind, message}` — the kind under the engine's own surface-kind grammar, `^[a-z][a-z0-9-]{0,63}$`, refused as `422 invalid_request` otherwise — and is `verbs::surface`: `{surface, state}`, the queued surface's id and `queued`. A message with nothing in it once trimmed is the engine's refusal.
- **`POST /api/v2/runs/{run}/attest`** takes `{reference}` and is `verbs::attest`: the same receipt a reply carries, for the planner's own `attest` of a ready human action.
- **`POST /api/v2/runs/{run}/stop`** takes `{force?: false}` and is `verbs::stop` with the acting session. A run another session owns is `409 not_owner` naming the owner unless the body forces; a forced stop is journaled forced with the owner it overrode, as `onepipeline stop --force` does; and an **unattributed server owns nothing**, so it is refused every stop it does not force. The payload is `verbs::Stopped`: `{run_id, stopped, owner, forced, teardown}`. A teardown that was not clean is not a stop — the run is still running — and is `409 not_stopped` carrying the engine's own account of what it could not reach.

**The browser's graph-override controls** are this repository's, and they add nothing to the wire. The reply composer offers a `set-node-sets` and a `set-run-node-sets` shortcut beside every other op: the first takes a node id and an ordered list, the second an ordered list alone, and each list is edited in place — an entry a row, added, moved up or down, removed, or loaded from the list the served graph holds for the same target (a node's `sets`, or `run_node_sets`). Composing renders exactly the engine's command, `{"op":"set-node-sets","id":…,"sets":[…]}` or `{"op":"set-run-node-sets","sets":[…]}`, under `version` 3, into the editor; a list with no rows is composed as `"sets": []`, never omitted, because an edit that names no list replaces nothing; and a blank row is refused by its position before anything is sent, while each entry's `PATH=VALUE` grammar is the engine's to read. What is sent is still the editor's text, byte for byte, so an envelope typed by hand — any op, any list — reaches `verbs::reply` as typed. The fields the engine owns are quoted from its `docs/contract.md` and its `channel::Command` and `plan::Node`, never restated here: `tests/fixtures/reply-commands.json` is the drift gate, pinned by `tests/contract.rs` to the fields that `Command`'s own schema declares and to `Node` keeping `sets` in order, and held by `packages/dag-model`'s own tests to the browser's `replyCommandSchema` and `planTaskSchema` — where a node's `sets`, on a plan task and on an `add`, a `retry` or a `requeue` amendment, is kept as written, `[]` included.

#### Shutting down the host

`POST /api/v2/shutdown` takes `{scope: "host", grace?: seconds, force?: false}` and calls `verbs::shutdown` with `ShutdownScope::Host` under the server's acting session. Every non-host scope is refused with `400 removed_shutdown_scope`, naming the rejected scope. A missing scope or malformed body is `422 invalid_request`. `grace` is integer seconds, omitted for the engine's default grace; `force` skips the interrupt and wait. Host scope proceeds over ownership and names each owner in the SDK's report.

The envelope carries `{scope, root, grace_seconds, forced, complete, runs, not_pushed, not_pushed_unread, rendered}` from the SDK. An incomplete teardown still answers `200` with its report so the operator can read what survived. `GET /api/v2/unwatched` remains the SDK's report for the acting session, including its optional `session_key`, for the Host page.

#### The read verbs

`GET /api/v2/runs/{run}/status` is `verbs::status(Some(run))`: `{run_id, liveness, unread_surfaces, node_status, summary, rendered}` — the run's driver liveness, its unread surfaces as `{count, oldest_seconds}`, every node's status as the run last settled it, the run's one-line summary, and the text `onepipeline status RUN` prints. `GET /api/v2/host` is `verbs::host`: `{rendered, unreadable?}`, every live dispatch on this host as that verb prints it and the roots it refused. `GET /api/v2/runs/{run}/results` is `verbs::results`: `{run_id, rendered}`. `GET /api/v2/goals` and `GET /api/v2/runs/{run}/goals` are `verbs::goals` given no run and given one: `{rendered, unreadable?}` and `{run_id, rendered}`. `GET /api/v2/runs/{run}/transcript?node=ID` is `verbs::transcript`: `{run_id, node?, rendered}`, and a node this run never dispatched is the engine's refusal rather than an empty transcript. `GET /api/v2/runs/{run}/telemetry` is `verbs::telemetry(Some(run))`: `{run_id, telemetry}`, the SDK's own document for the run — the one `onepipeline telemetry RUN` prints, carrying its own `schema_version`. In each, `rendered` is the SDK's own rendering of its typed result, byte for byte what the binary prints, because those verbs' results are rendered views of a folded run rather than records: an agent reading the CLI and a person reading this route read one text.

#### The agents a run launched

**Every agent a run launches is visible, automatically, whatever the agent structure of the repository it ran in — and the transcripts stay where each oneharness put them.** The engine overlays three variables on every dispatch it starts: history on, the run's **pointer file** — `oneharness-sessions.jsonl` under the run root, `RunPaths::oneharness_sessions()` — and its labels, so every oneharness turn under that launch, however it was reached, appends one line to that file saying where its session went. The engine sets no history store: a repository's own `history_dir`, or the store its environment names, or the platform default, is honoured untouched, and the pointer line says which. The label vocabulary, the pointer file and the entry shape are the engine's (`onepipeline::agents`) and oneharness's (`HistoryPointer`), stated in those crates' own contracts and never restated here; this API reads them through `verbs::agents` and `verbs::project_agents`, which open **only the pointer file** — never a store listing, never the locking indexed reader, never a spawned `oneharness`, and never a session file.

`GET /api/v2/runs/{run}/agents` is `verbs::agents(AgentScope::Run)`: `{run_id, sessions, skipped}`. `GET /api/v2/runs/{run}/nodes/{node}/agents` is `verbs::agents(AgentScope::Node(NODE))`: `{run_id, node, sessions, skipped}`, the lines whose `onepipeline.node` is that node — a node that dispatched nothing is an empty list, not an error, and so is a run with no pointer file, which is one an earlier engine launched or one that has dispatched nothing yet; a pointer file that is there and cannot be read is the engine's refusal. `GET /api/v2/projects/{project}/agents` is `verbs::project_agents`: `{project, sessions, skipped}`, the union over every run whose summary names that project, in the listing's order; a project no group of `GET /api/v2/projects` carries is `404 project_not_found`. `sessions` is the SDK's own `Agents.sessions`, one entry per oneharness session **grouped by `history_session`** in the order each first appeared, served as the SDK serves it: `history_session` (the session file's stem), `name`, `history_dir` (the store, absolute), `history_project` (the project slug), `history_file` (the session file, absolute), `project` (the directory the harness ran in), `started` (the earliest start among its lines, RFC 3339 UTC), `labels` (the engine's `onepipeline.run_id`, `onepipeline.project`, `onepipeline.scope` — `node`, `observer` or `pr-author` — `onepipeline.node`, `onepipeline.step` and `onepipeline.attempt`, each present exactly where the engine's contract says, and beside them whatever the repository stamped, such as a `role`), and `runs`, the harness runs the session recorded in file order, each `{history_id, harness, variant?, harness_id, started}`. `skipped` is how many lines the reader counted and did not read — a torn tail an interrupted writer left, or a foreign line — and it is a fact about the file, so it is the same count whatever the scope.

**Each entry opens to its transcript through the existing `oneharness_session` artifact resolution, and through nothing else.** A pointer line carries `history_dir`, `history_project` and `history_session` in the same spelling as the `oneharness-session` record `oneagentgraph` publishes, and each harness run's `history_id` is the artifact id: `GET /api/v2/runs/{run_id}/artifacts/{history_id}` serves that harness run's record from the session file the line names, resolved exactly as the paragraph on that artifact kind states — `find_session_path` and `read_session_display` over the linked `oneharness-core`, every component checked and the resolved path confined to the store the line named, and never a spawned `oneharness` or the locking reader. The artifact route resolves an id no envelope of the run recorded by reading the run's pointer file for it, so a session only the pointer file names — a nested harness turn a worker ran, a judge's own — opens the way a relayed one does. Beside the SDK's fields each entry carries **`run_id`**, the run whose pointer file the line is in, which is the run that artifact route is asked under: a run's or a node's listing names it outright, and a project's — the union over its runs — reads it off the `onepipeline.run_id` label the engine stamps on every launch, leaving it off an entry that carries none. That is the whole of what this API adds beside the SDK's record.

**Schema 19 is the agent count.** The run detail's `run` gains **`agent_count`**, and each group of `GET /api/v2/projects` and the body of `GET /api/v2/projects/{project}` gain **`agent_count`**: how many sessions the corresponding agents route answers — `verbs::agents(Run)` for the run, and for a group the union over its runs grouped by session exactly as `verbs::project_agents` groups them. It is `0` for a run with no pointer file, never absent for that, and absent only where a pointer file is there and this build could not read it — the discipline every unmeasured figure here keeps, served absent rather than as a zero. Every field 18 served is served with the same meaning and the same value, so a client written against 18 reads a 19 payload unchanged; the version moves because a client that has never seen `agent_count` reads a run under which a dozen agents ran as one nothing was launched for.


**Schema 21 is a run's graph overrides.** Each task of the graph's `plan` gains **`sets`**, the node's ordered `PATH=VALUE` list as the engine's fold holds it after every accepted `set-node-sets` — the plan's own list where no edit replaced it — and the graph gains **`run_node_sets`**, the run-wide list every future node dispatch composes before a node's own: the latest accepted `set-run-node-sets`, and the launch's `node_sets` where none was accepted. Both are the engine's fields, served as it records them and in its order, and both are **omitted when empty**, so an empty replacement — a list someone cleared — reads exactly as a list nobody set; a step carries none. Every field 20 served is served with the same meaning and the same value, so a client written against 20 reads a 21 payload unchanged; the version moves because a client that has never seen the lists shows a node about to dispatch under another model or harness config as one dispatching under the graph as written.

**Schema 22 adds `event_id` to live activity.** Each activity entry names the exact node timeline event it summarizes, using that timeline event's producer `record_id` address (`stream.seq`). The header links to that event without guessing from a timestamp. A run-scoped event stream emits existing activity as `activity.changed` immediately after its opening snapshot when that activity is non-empty, so opening a quiet run still shows its last activity. All other payload fields keep their meaning.

**Removed-route version exception.** Removing a route ordinarily moves the API major. The browser supervision routes are an explicit exception: API version 2 and every remaining `/api/v2` path stay in place because their only client is the browser bundled in the same binary and shipped with this removal. Moving all paths would break unrelated clients. Requests to a removed supervision route answer `404 removed_route` naming the path, API 2 schema 22 as the removal contract, and this binary's serving release. The binary no longer drives runs, including through hidden CLI verbs. Shutdown accepts host scope alone; the browser keeps Stop and host shutdown.

`/healthz` is the one response that is not enveloped — liveness must answer without reading run storage, so it has no schema version to read one from — and it carries two fields: `status`, whose only value is `ok`, and `onepipeline_version`, the `onepipeline` release this binary links, read from that crate's own `VERSION` rather than restated here and served as a validated `MAJOR.MINOR.PATCH` — a body naming a release nobody could have published is refused at the parse rather than compared against. A host that pins the engine writing a run store and separately pins this reader of it has nothing else to prove the two are the same release, so the reader says which one it is rather than leaving it assumed.

Payloads keep the telemetry schema-version discipline and serve schema 24 including `dispatch_id` — schema 10 was where `dispatch_id` landed, and 11 is that discipline exercised: an unmeasured timing is served `null` rather than `0`, so a lane nothing measured can no longer read as a measured zero. Anything the API computes that is presentation-worthy lands in the onepipeline SDK/CLI first: the agent reading the CLI must have the same or better visibility than the human in the UI.

Schema 12 answers, per node in flight, whether the run has a turn it can address for it — the precondition a planner needs before choosing between correcting a node and cancelling it. `node_control` carries one entry for every node recorded as `running` and for no other, and each entry is `{addressable, member?, reason?}`, with `reason` present exactly when `addressable` is false. A node whose turn this run cannot address reads as `addressable: false` carrying the reason — never as an error and never as an absent value — and where an interrupt has already been attempted the reason is the producing library's own words for what it found.

`addressable` means **this run has a turn it can address for that node** — the engine's own precondition for delivering a note into a running turn — read from whether a member is in a turn and from the outcome of every interrupt already attempted, which is published for every attempt whether or not it landed. It is not a claim that the harness will accept a redirection. No published component exposes an authoritative *current-turn* control state outside the process running the turn: onejudge reports `control` only on the finished run, the live provider accessor is in-process only, `oneagentgraph`'s spawn-time record is provisional for every member whatever its harness, and the control protocol's only verb is `interrupt`, which costs the turn. A previous dispatch's report is not a substitute and is never read as one — `provider.control` is asked for per run and reset for the next. `src/AGENTS.md` records each closed route and the upstream change that opens one.

**Schema 13 is the removal of rounds.** Execution in the onepipeline SDK is continuous and dependency-driven: a node — and each step within a lifecycle node — dispatches the moment its dependencies settle `done`, nothing batches them, and the envelope's `round` label is deprecated and stamped by nothing. So the payload's `rounds` array is replaced by one **`graph`** object describing the run's whole state, and no `round` survives anywhere in a response. A client reading 12 must not read a 13 payload: the array it indexed is gone, not renamed. `graph` is `{run_id, plan, node_states, node_status, node_gated_by, node_control, node_results, decisions, attestations, result, last_seq}` — one desired graph with every committed live edit applied, and one recorded `result`, which the SDK rewrites whenever a driver closes out.

**Schema 14 is the transcript a dispatch really had.** A conversation turn is assembled from the **stored onejudge report** the settling member left, and not from journal envelopes alone — the journal records that a session reported and what tools it called, which is almost none of what a transcript is. A settlement carries no `session` label and needs none: a session id is `{stream}.{member}`, so the settlement a transcript belongs to is the one whose stream and member spell it, and the run's copy of its report is located the one way this contract allows, through `RunPaths::report_for(STREAM, SEQ)`. A turn is joined to what the report says about it by the producer's own 1-based turn number — the **agent's**, which is the only side a transcript has rows for — which `turn-started` carries and which is the counter the report shares between `telemetry.sessions` and `telemetry.attribution`. **The report is the set of turns and not only their content**: every turn it recorded is served, whether or not any envelope of the run ever named it — a producer relays a `turn-started` for the turns it brackets and none at all for a member whose turns it never bracketed, so a dispatch the journal knows one turn of is regularly one the report holds fifty of, and reading the report only where a relayed record already stood served all fifty as one empty row. **And a relayed record that numbers no turn is then not a turn**: the single `turn-completed` `oneagentgraph` 0.2 published per *dispatch*, beside the settlement, carries the member's whole total rather than any turn's, so serving it beside the report's turns would be a turn the report does not have — no prompt, no reply, and every one of the dispatch's dollars billed to it. What that record spent is the run's own `usage`, which is where it is served. The rule is unchanged by that producer having since corrected itself: 0.3 numbers every `turn-completed` and names the party that took it, so a record it wrote joins the report's turn by the pair it carries, and the unnumbered ones the rule is about are the ones already on disk. The count of turns a transcript serves, the `turns` counted beside a node and the run, and the turn a timeline event names are one reading of one fold, so no two of them can disagree — and a turn no record produced is named by nothing on the timeline, because nothing relayed it. Neither the shape nor the version moves for any of this: a client reading 14 reads the same turn object and reads more of them.

Under 14 the fields `DagConversationTurn` has always declared are filled: **`user`** is the prompt the simulated user gave and is never the dispatch's persona name — who was asked is not what they were asked; **`assistant`** is the reply that turn wrote, and `null` for a turn whose report recorded none; a **tool event** carries the observation it returned wherever the report holds one, and `output: null` where the trace exposed none; **`usage`** and **`durationMs`** are what *that turn's own invocation* spent and took, read off the candidate that `ran` in the turn's `role: agent` attribution — the report's top-level `usage` is the whole dispatch's total over both sides, and serving it per turn would repeat one total on every one; and **`startedAt`/`finishedAt`** are that turn's agent-side `telemetry.sessions` bounds where the report holds them and `null` where it does not. **No figure recorded against the judge is ever served on an agent turn** — not a bound, not an elapsed time, not a usage count. `role` in `telemetry.sessions` says which *side ran* and `role` in a transcript message says *who wrote it*; they are two vocabularies that share no word and are never read as one. **`failureKind`** is the classified reason `oneharness` gave for the candidate that `ran` the turn, on the agent's turns as on the judge's, and `null` where the report attributes none; and the report's whole **attribution** of the turn — which harness ran, which fell through and why, and every candidate's own status and classified failure — rides on the turn's **`unknown`** map as `attribution`, verbatim as `onejudge` records it, because a chain that fell through before the candidate that ran is a fact the turn's own fields cannot carry. A harness that reported it would run a turn under a model other than the one asked for is refused before a token is spent, and that refusal is exactly such a fact: it reaches a reader as the `model_mismatch` kind on the candidate that refused and the `model-mismatch` reason on the fall-through beside it, both in `oneharness`'s own words. A session whose member has not settled, whose report the run does not hold, or whose document cannot be read as a report is filled from its own journal records rather than emptied — including that dispatch-level `turn-completed`, which is then the only account of the dispatch anything holds and is served as the turn it always was. The paragraph below states that reading in full.

Under 14 a session the run holds **no readable report for** is filled from its own journal records instead, which is the whole of what a dispatch still in flight or one whose member died has: a report exists only once a member settles, and a member that dies never writes one. The producer publishes the four records that reading rests on and every field they fill was already declared here, so no field is added and this version does not move for them. `turn-started` carries `{turn, role, instruction, instruction_truncated, started_at}` and its `instruction` is the turn's **`user`**; `turn-message` carries `{turn, role, text, truncated}` and an **assistant**-role one is the turn's **`assistant`** — a session that published none reads as `null`, and the supervisor's own words reach a reader as the prompt of the turn they opened rather than as a reply; `turn-completed` carries `{turn, role, usage, started_at, finished_at}`, which are that one turn's **`usage`**, **`startedAt`**, **`finishedAt`** and — as the difference between the two, in whole milliseconds — its **`durationMs`**; and `turn-activity` carries `{kind, name, detail, truncated, output, output_truncated, tool_call_id, index}`, whose `output` is folded onto the **tool event** it answers. **A turn is joined to its records by the pair of `turn` and `role`, never by the number alone** — the two sides of a two-party member number their turns independently, so a join on the number reads the supervisor's instruction and the supervisor's cost as the agent's. **An observation is paired with its call by `tool_call_id` where both carry one and by the recorded `index` where neither does, and never by position in the served array**; one that answers no call the turn published is served as an entry of its own rather than dropped. A record from the producer that predates this pair — a `turn-started` numbering a turn and saying nothing about who took it — joins nothing, and its turn is served as it always was.

**A transcript's turns are the agent's turns, and this is true of both readings.** A two-party member relays both sides into one session and each side numbers its own turns from 1, so the supervisor's records are its own invocation rather than a row beside the agent's: what it was asked is the reply it is answering, what it said is the next instruction, and what it spent is its own. Both reach a reader where they belong — its words as the **`user`** of the agent turn they opened, its cost in the run's `usage` — so a session serves one row per agent turn and the rows alternate the prompt with the reply for the whole of the conversation, with no party's words served against the other. Serving the supervisor's side as rows of its own put the agent's reply on the user side of a row and read every two-party dispatch at twice its length; against a stored report, where the join is the number, it matched each of the report's turns to both sides and served that turn twice — one row of it correct and one attributing the agent's prompt and reply to the supervisor. A `turn-activity` published from inside the supervisor's own invocation is likewise no agent turn's **tool event**, and is served on no turn rather than folded onto the agent turn before it. A record that names **no** party is the agent's: the producer that predates the party runs one side and relays it, so there is no other side for such a record to belong to. The supervisor's records are still events of the run and are still listed on the timeline, and a timeline event produced by one of them **names no turn** — the transcript has no row for it to name, and pointing it at the agent turn before or after it would be this API guessing which. Neither the shape nor the version moves for this — a client reading 14 reads the same turn object, and reads only the rows that are turns.

**Where a session has both a stored report and live records, the report is the whole of the reading and the records above are not read at all.** The report is complete and unbounded where the journal is bounded, so a merge of the two could disagree with itself about one turn — a cut reply beside the whole of it, or words on a turn the report says produced none. What the journal bounds it says so, in the producer's own words: an `instruction_truncated` or a `truncated` reaches a reader on the turn's **`unknown`** map — the field this shape already carries a producer's own record on — and an `output_truncated` sits on the tool event, beside the `output` it is about. Each is present exactly when the producer cut something and absent otherwise, and a turn's served `index` on a tool event is that producer's own numbering where it published one. The whole of any cut text is in the report the member stores when it settles. A bound that is not an instant is served absent, on the same terms a report's unreadable bounds are, and a figure nothing measured is absent rather than a zero.

**Schema 26 is every turn read whole from its transcript.** `oneagentgraph` 0.8 no longer copies a turn's content into its records when history is on: a `turn-started`, `turn-message` or `turn-activity` carries a **`transcript`** reference — `{history_dir, history_project, history_session, history_id}`, and `index` with an optional `tool_call_id` on an activity, as that library's `docs/contract.md` states — and none of the bounded copies. Every conversation and every harness session this API serves reads its text through the linked engine's **`views::transcript`** resolver by that reference: a turn's **`user`** is the prompt the candidate's opening history line recorded, its **`assistant`** the candidate's closing text with the `message` events it streamed, its **`reasoning`** the `reasoning` events, and each **tool event**'s `input` and `output` the event line's own — `input` the structured value the harness recorded, never a summary — whole, and live while the dispatch is in flight, because the history file is written as the turn happens and the resolver reads a file still being written up to its last complete line. So a session recorded with references carries **no** `instruction_truncated`, `truncated`, `output_truncated` or `input_truncated` on any turn. **A reference the resolver cannot resolve is served as the resolver's own line, `transcript unavailable: <path>: <why>`** (`missing-file`, `missing-entry` or `unreadable`), in the place of the text it stood for — a prompt, a reply, a tool's output — never as a blank or an empty conversation; a reference whose file resolves outside the store it named is `unreadable` and is not opened. A live tool event gains **`toolCallId`** where the harness minted one. **A run recorded before references keeps its copies**, and the copy is the last of three readings rather than the first: the member's stored report where the run holds one (the paragraph above), else the whole entry in a history file the run itself names — the session's own `oneharness-session` records, and the run's pointer-file lines stamped at the session's node — whose prompt begins with the turn's instruction copy — and the turn's reply and tool outputs only from that same invocation, whose reply begins with the copy or whose output ends with it, because two turns can return the same output; and only where neither holds one, the copy, carrying the recorder's own flag — `instruction_truncated` or `truncated` on the turn's `unknown`, `output_truncated` or `input_truncated` on the tool event — so a reader is told the recorder cut it and no whole copy exists. A live-activity entry gains **`description`** under schema 26, the resolver's one line for the call. Every other field 25 served is served with the same meaning and the same value; the version moves because a client written against 25 shows a cut prompt as the whole of one and has never seen `description`.

Under 14 a settled dispatch also serves **the judge's own conversation and the lane it is reachable through**, and neither schema version moves for it: it is a conversation and a span, not a field or a vocabulary member. Nothing relays a judge session and no producer change can — a plan node dispatches one graph member and the judge runs *inside* onejudge, so there is no `session` label for the transcript listing to group on and no relayed record for a timeline span to be bracketed by. The stored report is the whole of what any run holds about that side, and it holds it only once the member settles, which is why a dispatch still running serves one lane. Its id is the worker session's with `.judge` after it, so the conversation route resolves it through the same lookup as any other; it is attributed `transportRole: judge`, and its `agentRole` is **the supervised member's own** — the judge is a *party* of a two-party member and not a member of its own, no graph declares one and the run records it only inside that member's report, so under schema 17 its `agentRole` is read exactly as the agent side's is, from the run's declarations, and is absent where that side is served none; the transport word is what tells the two sides of one member apart, as it tells the lint tier from the work it reads — and it names the dispatch it supervised as its `parentConversationId`. One turn per `role: judge` `telemetry.sessions` row — the only per-turn bounds a report holds for that side — carrying that row's start and end, and the model, elapsed time and usage of the candidate that `ran` in its `role: judge` attribution — the one carrying that row's own `judge` label, because a stacked panel runs every judge on one supervisor turn and a join on the side and the turn alone hands each of them the first judge's invocation — with a figure the provider never reported served absent rather than as a zero. **No text is served against a judge turn**: the report keys none to one, and the two sides number their turns independently with nothing recording which judge turn wrote which instruction — the judge's authored prose reaches the wire already, as each agent turn's `user` message. One closing turn carries what the report keys to the *dispatch* instead: every criterion it judged, the verdict and reason it returned for each, its closing assessment, why it completed and whether it stopped early — served whole, because the bound this API puts on an artifact's bytes is not one it puts on a report-backed read — and with no bounds and no usage, because the report records none for it. The lane beside it is served as a **sibling of the dispatch span**, at the same node, step and `dispatch_id`, drawn over those same rows: it opens at the earliest of their starts and closes at the latest observed finish, and a row whose end was never observed leaves it open under the rule every unclosed span here is served by.

**A turn a stacked panel judged carries each judge's decision on it.** The report this API links is onejudge's schema 12, which records per supervisor turn what every judge of a panel decided — and a supervisor turn is numbered by the agent turn it judged, the number the report and `oneagentgraph`'s `judge-decided` record both carry. So that agent turn's row gains **`judges`**: one entry per judge, in the panel's own list order, each `{judge, kind, decision, reason}` — the judge's label within its panel, its provider kind (`oneharness`, `llmlint`, `command`, …), what it decided in onejudge's own spelling (`done`, `continue`, `no_instruction`, `unparseable` or `error`), and its own reason, or the error's message for an `error`. It is read from the stored report's `judge_decisions` where the run holds a readable report, and from the session's own `judge-decided` records where it holds none — joined to the session by `{stream}.{member}`, because those records carry no `session` label, and to the row by the turn number — on the precedence every other field of a turn keeps. It is **absent**, never empty, on a turn no judge decided on, which is every turn of a dispatch judged by a bare provider rather than a panel: nothing is synthesized. The supervisor's own words still reach a reader as the next turn's `user`; `judges` is what each judge said about the turn it sits on. **Schema 16 is this field.** Every field 15 served is served with the same meaning and the same value, and `judges` is absent rather than empty on every turn nothing decided on; the version moves because a client that has never seen `judges` reads a stacked panel's dispatch as though no judge had said anything about any turn of it. A `judge-decided` is refused by no route that reads a member's records — it is an event of the run like any other, and it is not a turn: it names none of its own and counts toward none.

14 also removes the one reading that measured nothing. A usage record on this wire is `onejudge::Usage` — `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `cost_usd` — because `oneagentgraph` relays a settling member's usage copied verbatim out of that report; the six keys this API read one by were spelled the way a declared-but-unwritten type spells them, so every served cost and token count was `null`. There is no `duration` among them and there never was: a turn's elapsed time is its attribution candidate's `duration_ms`, served on the turn it belongs to as `durationMs`. The per-party `*_model_ms` lanes a run's `timing` carries, their fractions, and `node_work_ms` are therefore served **absent**, with the presence flags beside them saying so — nothing in this stack reports how long a party spent inside a model, and an invocation's wall clock is neither a model's clock nor a party's. A tool call's own interval is unmeasured on the same terms.

`decisions` is what replaces a round's own account of why a run is not moving. The only thing that pauses anything is a **decision point**, and it pauses only the subtree that depends on it — a ready `kind: human` node's attestation, or a blocking surface nobody has answered — while independent branches proceed. Each entry is `{id, kind, unblocks}`, mirroring the SDK's own `decision-pending`, and it is absent from the list again once `decision-cleared` releases the subtree. `phase` names a continuous phase — `starting`, `dispatching`, `deciding`, `surfacing`, `waiting`, `settled`, `finished` — rather than a position in a batch, and `node-ready` is the kind that reports a node became eligible to dispatch. Plan schema 2 retired `done_when`, so no plan task carries one: a node's bar is the `## Acceptance criteria` section of its own task prose, which is what the judge is handed.

Timeline schema 4 carries the redirection itself. An event produced by a `turn-interrupted` or by an `edit-committed` that added context to a node carries `redirection` — `{delivered, member?, input_bytes?, reason?, delivery?, node_id?, reached?}` — so a turn whose behaviour changed mid-flight shows the moment the planner changed it, and whether the note went into the running turn (`live`) or onto the node's next dispatch (`deferred`). The engine that links here records a note as a `note-delivered` operation rather than the `context-added` its predecessor wrote, and says which **party** of the running conversation took it: that word is served as `reached` — `queued`, `worker`, `supervisor`, `judged-with`, or `carried`, the one that means no turn took the note and it rides the node's next dispatch — and the same `delivered`/`delivery` pair is read off it, so a client reads one pair whichever engine wrote the run. `reached` is present exactly when the record named a party; a record written by the older engine carries none. An `edit-committed` additionally carries the `author` that submitted it, served as the **open word** the record spelled: an omitted author is `planner`, and every other author is one the run's launch declared in its bus configuration together with the operations it grants — so an observer's self-applied fix and the planner's own decision are two different facts about one graph, and a reader is shown the author under whatever word the host chose for it. This API keeps no list of authors: a run written by the engine that named its observer `monitor` still serves that word, and a run whose launch declared `sentinel` serves that one. The engine reports every non-planner author's applied edit back as a surface of its own kind, `edit-applied`, whose `source` is that author's word; it is served as any other surface is, under timeline schema 9 below.

**Timeline schema 5 is continuous too.** The run itself is the single root span (`kind: "run"`), not one span per round; no span or event carries a `round`; and every span id is keyed by what it identifies — `run.RUN`, `node.ID`, `dispatch.SESSION`, `publication.ID`, `verification.ID.ARTIFACT`, `rollup.ID.…`, `human-wait.ID` — rather than by a round number. A node has one span however many times it was dispatched: the SDK re-asks a dispatch that produced nothing and records each attempt as its own `node-dispatched`, and every attempt is the same node's same work.

**Timeline schema 6 says what one lane was doing, and when.** Under 5 a node's own window was every span's window: each `dispatch` span carried the node's first dispatch and last settlement, and each `scope=run` `rollup` the same pair — so a node the engine re-asked served one span per session over one identical interval, and a drafting turn that took a minute was drawn across the hours of work it drafted for. A session is now bounded by **the attempt that ran it**. It opens at that attempt's `node-dispatched` — the latest at or before the session appeared — and it closes at the earliest of the next `node-dispatched`, the `node-settled` that followed it, the `session-closed` that took its worktree away, and the `member-settled` or `member-died` that ended the session itself, the last of these joined to it by its `{stream}.{member}` id. Nothing may close it before the last thing it said, and where none of those records exists it is served with a null `ended_at`, which is a session still running. **Every session of one attempt opens at that attempt's dispatch**, including one the attempt reached only after another had finished: an attempt is the unit a session is bracketed by, the run records no boundary between the members inside one, and a session is never opened from its own first word. So a node dispatched three times serves three spans over three different intervals, while a lifecycle node dispatched once serves its worker and its drafting turn from the same moment and closes each where the run said that member was over. A category's rollup covers the sessions in it rather than the node they ran under.

A **`publication`** opens at the first record that is publication work rather than at the worktree the dispatch was cut into: `onevcs` cuts a worktree when the node is dispatched, so under 5 the span covered the work being published rather than the publishing, and a node that never published was drawn publishing to the end of everything it recorded. A node that did no publication work serves no publication span at all, and `session-closed` now closes one — ranked behind a merge, a conflict and an opened change, because it says only that nothing more can happen on that branch. A publication the run ruled on carries its `status`; one whose worktree simply went away carries none.

A span's **`agent_role`** is read from the `member` the run recorded for the session, falling back to the persona only where no member was stamped. A persona is a style a host invented — `engineer`, `docs-writer` — so reading a role off one dropped every session a host had not named after a role, and a run-scope reading showed an empty `Worker` lane beside the one drafting turn whose persona happened to be the word `pr-author`. Under 6 the `monitor` member was served as `orchestrator` and `agentRoleSchema` was a closed vocabulary of five words; timeline schema 10 and telemetry schema 17 below open it. The two rules a client already depended on are unchanged: a span the run never closed is served with a null `ended_at` and is never given an invented one, and a span nothing measured is served absent rather than as a measured zero.

**Timeline schema 10 and telemetry schema 17 derive the lanes from the run's own graph declarations.** A session's `agent_role` — on a `dispatch` span, on the `rollup` standing for a category of them, on a run's session links and on a conversation's attribution — is **the member name the run recorded for it**, served exactly when the run's recorded graph declarations name that member. `oneagentgraph` writes a run record for every graph it runs, carrying the members that graph declared; the observer graph's is the run the launch record names as its `graph_run` and among its `observer_runs`, and each node graph's is the **stream** its records were relayed on. The reader reads those records from the state directory the engine itself resolves — `ONEAGENTGRAPH_STATE_DIR`, else `~/.local/state/oneagentgraph/runs` — and no member and no role word is built into it: a host's `monitor` member is served as `monitor`, its `check-in` as `check-in`, and a member named `sentinel` as `sentinel`, in whatever order the run relayed them. A session whose stamped member no declaration names is served no `agent_role`, and the persona beside it is never consulted; a session that stamped no member is read by its persona — its own record's, or the `node-dispatched`'s where its record carried none — and served that word only where a declaration names it as a member, never through a list of persona words. A conversation's `attribution.agentRole` is therefore **optional** under 17, where 16 defaulted it to `worker`. `agentRoleSchema` admits exactly `oneagentgraph`'s member-name grammar — letters, digits, hyphens and underscores, `config::is_member_name` as `MemberName::parse` states it — and nothing narrower; a client draws one lane per distinct `agent_role` a payload serves, in the order the payload serves them, labelled with that word. The `run` span the engine's own driving is drawn under keeps its kind and its label: it is the engine's lane rather than a member's, and it is the one lane that is not one — the judge's lane is the supervised member's, under that member's word, as the paragraph on schema 14 above says. Both versions move because a client that switched on the closed vocabulary exhaustively misreads an open one; every other field is served with the meaning 9 and 16 gave it.

**Timeline schema 7 carries the release a record was about.** Six kinds say what a run's releases did, across the two producers that record them: `onevcs` writes `release-probed` (`{identity, target, form, outcome, version, elapsed_ms}`, automated targets only — nothing but a person can answer for a human step), `release-acknowledged` (`{identity, target, version, landing_commit, actor, superseded}`) and `release-observed` (`{identity, target, style, version, landing_commit}`); `onepipeline` writes `release-wait` (`{node, awaiting: [{dep, identity, target, style, action, since, waited_seconds, last_answer}]}`), `release-arrived` (`{node, dep, identity, target, style, version}`) and `release-adopted` (`{node, delivery, versions: [{identity, target, version}]}`). An event produced by any of the six carries **`release`**, which is that record's own fields and nothing defaulted — each present exactly when the record carried it, on the discipline `redirection` already keeps, because the two producers know different halves of one sequencing and a field filled in here would be this API saying something no record did. `style` is `automated` or `human-step`, and `action` is carried only on a **human-step** `awaiting` entry, because that is the one wait somebody has to be told about: a client can pick out the waits that need a person from the entries that name one. `last_answer` is the producer's own word for what the last look found — `not-released`, `awaiting-human-step`, `not-answered` or `not-landed`. Every other event is byte-for-byte what 6 served; the field is additive and optional exactly as `redirection` was in 4.

**Timeline schema 8 draws what a ready node was waiting for.** Under 7 the interval between a node becoming ready and its dispatch is empty, which reads as the harness having done nothing — when what really happened is that the node sat queued behind the operator's own other work. A node the engine recorded a hold for now serves a **`queued`** span, `kind: "queued"`, parented on the node's own span at `queued.NODE.INDEX` — keyed by the record that opened it, because one node is held many times over and the hold is what each span identifies. It carries **`reasons`**, one entry per thing holding the node at that moment, so a node held by two things is told apart from a node held by one from the array alone. Each entry names its `kind` and that kind's own fields, and `onepipeline` writes four: `dependencies` (`blocking`, the dependencies that have not settled `done`, as the graph names them), `concurrency` (`ahead`, the dispatches in flight ahead of it, and `limit`, the run's concurrency), `decision` (`reference`, the decision point holding the subtree it is in) and `release` (`awaiting`, the dependencies whose releases have not happened). `kind` is served **open**, exactly as an event's own `kind` is and for the same reason: the vocabulary is the engine's and released on its own schedule, so a reason a later engine writes reaches a reader as its own distinct reason rather than as a hold that has quietly lost one. What a decision or a release *is* stays on the `decision-pending` and `release-wait` records — these name only which one holds the node. Every other field is served exactly where the record carried one this build could read, on the discipline `release` already keeps, and an entry naming no `kind` at all is dropped; a record whose every entry was dropped serves no span, because a queued span carrying no reason would draw the empty interval back as an explanation nobody wrote.

The engine writes a hold when it **begins** and again whenever what the node is held by **changes**, and never on a pass where it is held by what it was held by before; `node-unheld` says it cleared. So each record opens a span that closes at the next record of either kind, and a node behind three running nodes that finish one at a time serves **three successive spans** — the first naming all three, the second the two that are left, the third the last — ending where the hold cleared and the dispatch followed. A node still held serves its last span with a null `ended_at`, under the rule every unclosed span here is served by. **A run recorded before the engine wrote any of this serves no `queued` span at all**: the gap it shows today is the gap it goes on showing, because a span inferred from a dispatch that came late could not be told from one the run actually recorded. Every other span and every event is byte-for-byte what 7 served; the kind and the field are additive exactly as `release` was in 7.

**Timeline schema 9 carries what a surface said.** A surface is the one thing a run raises *to* somebody — a check-in, a finding, a question that holds a subtree until it is answered — and its kind is an **open vocabulary**: the engine declares and acts on `check-in` and `finding`, raises `edit-applied` of its own, and relays every other well-formed kind a host defines (`^[a-z][a-z0-9-]{0,63}$`) unchanged, with its message, its source, its blocking flag and its unread accounting. So an event produced by a `planner-surface-queued` or by the `planner-surfaced` that consumed it carries **`surface`** — `{kind?, message?, source?, blocking?}` — each present exactly where the record carried it, on the discipline `redirection` and `release` keep, and a record that carried none of them serves no `surface` at all. `kind` is the word the host raised it as and `source` is the author that raised it, both served as recorded: a kind this build has never seen is a surface a host defined, not a payload to refuse, and the one closed list this API declines to keep is a list of either. A surface is counted wherever surfaces are counted whatever its kind — the run's `phase` reads `surfacing` while one is queued and unread — and a **blocking** one is served as the decision point it is: `graph.decisions` carries it under its `surface:N` reference with that surface's own kind as the decision's `kind`, and its subtree is released when the answer clears it. Additive exactly as `release` was in 7 — every other span and every event is byte-for-byte what 8 served.

**Timeline schema 11 carries where a change request's review stood.** `onevcs` opens every remote change request as a draft while its required checks run (`change-drafted` with `kind: "awaiting-checks"`), records each check as it moves (`change-check`), records the checks settling (`checks-settled`, `{url, id, head, verdict, skipped}`, `verdict` being `passed` or `passed-with-skipped`), and then lifts the draft (`draft-lifted`), lifts it before any required check ran because the repository's checks skip drafts and nothing is in progress on the pushed head (`draft-lifted-early`, `{url, id, base, awaited, grace_seconds, warned}`, beside the `draft-lifted` every lift writes), or — on a `change-open` identity whose approvals are required — keeps it a draft for its own user's review (`draft-kept-for-review`, `{url, id, base}`), the record behind a node settled `done` with the outcome `change-review-draft`. An event produced by any of those six carries **`review`**, that record's own fields: `name`, `required` and `state` on a check; `kind` and `base` on a draft; `base` on a lift or a kept draft, with `awaited`, `grace_seconds` and `warned` on an early one; `head`, `verdict` and `skipped` on a settlement — each present exactly where the record carried it, on the discipline `release` keeps, and a record that carried none of them serves no `review`. A check's **`state`** is one of `onevcs`'s five check states — `passed`, `failed`, `skipped`, `pending`, `no-verdict` — as the record carried it, and for a record written before `onevcs` carried one it is read from the record's `status` and `conclusion` on that library's own terms; **a skipped check is `skipped` and never `passed`**, and a verification record a skipped check stored is served `ok: false`, because a check that did not run verified nothing. A `publication` whose change was left open now closes where the run's watch of it ended — the last `checks-settled`, `draft-lifted`, `draft-lifted-early` or `draft-kept-for-review` after it was opened — rather than at the moment it was opened, and keeps the status `open`. Every word is served open, because the vocabulary is `onevcs`'s and released on its own schedule. Additive exactly as `surface` was in 9: every other event, and every span of a run that recorded none of those kinds, is byte-for-byte what 10 served.

**Timeline schema 12 says how a live turn took a note.** The engine that links here delivers a note with `deliver` of `live`, which interrupts the addressed party's running turn or reaches it at its end where it cannot be interrupted, `turn-end`, which never interrupts and reaches the running turn only once it ends, or `next`; and its `worker` and `supervisor` dispositions say which happened as `turn` — `interrupted`, where the running turn was interrupted and its replacement opened on the note, or `turn-end`, where the turn was left to end and the note reached it then. A `redirection` read off a `note-delivered` that carries it serves it as **`redirection.turn`**, beside the `reached` it qualifies; it is present exactly when the record carried it, so a record written before the field existed — and every other disposition — carries none, and a word outside the pair is a record this build cannot read, served as no `redirection` at all, as an unknown `reached` already is. Additive as `review` was in 11: every other span and event is byte-for-byte what 11 served.

**Timeline schema 13 counts producer identities once.** A repeated journal record with the same **`(stream, seq)`** identifies one record, even when a continued session relays it again. The first occurrence supplies the record; duplicates contribute neither additional events nor additional spans or counts in either timeline scope. Canonicalization precedes transcript numbering, so repeating a record cannot change a timeline event's transcript address. Event arrays are ordered by each record's timestamp, with journal position breaking ties. Journal order means the SDK's deterministic merged order, shared with its other views, rather than the physical append positions in `events.jsonl`. Session lanes open at their own first record and close at their own last record once a closure is recorded. Both scopes use those same bounds. This corrects dispatch session spans and their role rollups, whose older schemas opened at the node dispatch; baseline comparisons across schema 13 exclude only these session bounds and compare event arrays in stable timestamp order, while asserting the corrected bounds, timestamp order, journal tie order and group ownership directly. A run whose nodes all settled ends at its last node settlement; otherwise a recorded run stop, host shutdown or final driver exit ends it. Open spans close at that execution boundary. Commands recorded later remain events, without extending execution or idle. Across schema 13, baseline comparisons assert that execution boundary from settlement or termination and exclude only the run end and formerly open spans closed at that boundary, including their running-to-stopped status correction. Events additionally carry **`stream`**, **`seq`**, **`journal_order`** and **`record_id`**, preserving the producer identity and journal tie breaker separately from a transcript turn's `id`. Optional **`dispatch_id`** identifies the served run/node dispatch, and **`persona`** names the stamped persona. Node-scope events and spans belonging to a dispatch additionally carry optional **`dispatch_group`**: `id` is the stable dispatch/graph-stream/producer identity, `label` names the dispatch or its unnumbered drafter, `order` preserves unfiltered journal order, and `started_at` is that dispatch's `node-dispatched` timestamp. This ownership is computed from the whole journal, never from filtered events. Node-level records outside a dispatch carry no group. Missing groups remain compatible with older payloads. Optional **`fields`** is the nonempty object of recorded facts selected by the server's per-kind table; absent and empty facts are omitted. `gate-run` selects gate, verdict, seconds and log; `session-closed` selects outcome, branch and head; `node-dispatched` selects attempt, persona and reason. Unknown kinds still have their timestamp. Harness sessions recorded only in the SDK's pointer listing also have timeline spans, with optional **`dispatch_attempt`** naming the stamped attempt and **`harness_scope`** naming the launch scope and an `oneharness_session` reference opening the same transcript the Agents listing opens. Observer harnesses belong to the run; node and drafter harnesses belong to their corresponding session or node. A harness record's stated start and finish bound its lane; without a recorded finish it is a point at its recorded start labelled “no recorded end”. Harness-only entries open transcripts but contribute neither work nor idle in Overall. No field is removed.

**Timeline schema 14 describes every turn record in one line.** A `turn-started`, `turn-message` or `turn-activity` event gains **`description`**: the linked engine resolver's one line, at most 120 characters, for the entry the record points at — a shell call's command with its shell wrapper taken off, a file tool's verb and path, a search tool's pattern, any other tool's name and first argument, a message's or prompt's first line — or the resolver's `transcript unavailable: <path>: <why>` for a reference that resolves to nothing. It is served by this API and never derived by a client, so the browser and `onepipeline transcript` describe one call in the same words. A `turn-activity` event gains **`tool`**, `{index, tool_call_id?, turn?}` — the producer's index for the event within its candidate, the harness's identity for the call where it minted one, and the id of the conversation turn it was published inside — and, where it was published inside a turn of a session, the **`reference`** `{kind: "conversation", value: SESSION}` a turn record carries; its own `id` stays its own. That is where the event sits in the conversation, so a reader opening the row is shown that turn focused on that call. Every other event is byte-for-byte what 13 served.


**A node's result carries the release that carried its work.** `graph.node_results[NODE]` gains **`release`** — `{identity, target, style?, version}` — beside the `pr` it already carries, and it is **absent**, never null, for a node the run recorded no release for, exactly as `pr` is absent for a node that opened no change request. It is the newest `release-observed` on the merged store whose `landing_commit` is the commit that node's work landed as, which is also the `commit` its publication is served with. **The join is that commit and never a node label**: a release is observed long after the dispatch that produced the work has settled and outside any session of it, so nothing is there to stamp that envelope with a node, and a label lookup would find nothing on every run. Where such an envelope does happen to carry one it is corroboration and nothing is filtered on it. `style` alone is optional, because an envelope written before that field existed carries none. A record naming no identity, no target or no version is served no release at all: those three are what a release *is*, and this API does not invent the rest. Nothing here computes a release, polls a registry or runs a probe — this is a read surface, and everything about how a release is discovered belongs to the producers above.

**An artifact is served as `{id, kind, content, truncated}`, and where its bytes are read from is decided by what the producing library said it stored.** A log's body is the end of the file rather than all of it — a producer promises no size, and a read surface that streams an unbounded one into a browser can be made to exhaust its own memory — so `truncated` says whether anything was left off the front. A transcript (`conversation`, `oneharness_session`) and a `worker_report` are served whole, with `truncated: false`: each is read from its first word to its last, and a report's copy is already held to the size bound `retain` keeps it under. `kind` is the wire's closed reference vocabulary (`conversation`, `gate_log`, `worker_report`, `oneharness_session`, `pr`), read from the producer's own word for the artifact.

A **`worker_report`** — the report `oneagentgraph` records on every `member-settled`, which is the judge's ruling against each acceptance criterion, the follow-ups the worker surfaced, and why it stopped — is the one kind the run holds a copy of. `onepipeline` copies it into the run's own storage as the settlement is ingested, and **retention and resolution are one published promise**: this API resolves it by calling that SDK's `RunPaths::report_for(STREAM, SEQ)` on the envelope the artifact was recorded on, and never by restating that name or the sanitiser behind it. The artifact id names the stream but **not** the seq, which is why the envelope rather than the id is what locates the file. A settlement whose copy the run does not hold — `retain` refuses a report that is a symlink, is not a plain file, is misnamed, or is past its size bound — is `404 artifact_not_found`, never an empty body.

An **`oneharness_session`** is the conversation one oneharness invocation actually had, and it is the one kind whose bytes are **not under the run at all**. Nothing copies a session into a run: `oneagentgraph` publishes a pointer — `history_dir`, `history_project`, `history_session` and the `history_id` that is also the artifact's id — and the transcript stays in the oneharness history store on the host. So this API resolves one through the **linked engine's `views::transcript` resolver**, the same reading every turn record gets (schema 26 above): the invocation's prompt, every event it recorded in order — oneharness numbers a candidate's events contiguously from 0, so its events are the resolver's `index` from 0 until the file holds no next one — and the text it closed with, served whole and live as **`turns`**, one conversation turn in the shape a conversation's turns have, `status: "running"` and no reply for an invocation that has not closed. `content` is the invocation's own closing record — its harness, model, status, failure kind, timings and usage, read through `oneharness-core`'s `io::history::read_session_display` with `io::history::resolve_dir` for a record that named no store — as pretty JSON, whole, with its `prompt` and `text` the resolver's and its `events` left to `turns`; for an invocation that has not closed it is `{history_id, status: "running", prompt, text}`. A pointer at a file or an entry the store no longer holds is served, not refused: **`unavailable`** carries the resolver's `transcript unavailable: <path>: <why>` and the turn says the same in the prompt's place. Never `io::history::find_record_by_id`, which reconciles the store's index under an exclusive `flock` and rewrites it — a read surface must not stand in the way of the single writer the engine runs — and never by spawning the `oneharness` CLI. There is no flag and no config key here for that store: the record names it, and the fallback is the same default every oneharness process on the host resolves, because a second source for that path is how a reader and a writer come to disagree about where the transcripts are. **`history_project` and `history_session` come off a record, which is external input exactly as a URL is**, and each is checked as a bare name before anything joins it; a value that climbs, carries a separator, is absolute, or names a dot file is `404 artifact_not_found` rather than a file opened somewhere else on the host. So is a file that resolves out of the store it was named under.

Every other kind is a log the producing library stored beside the run, under its own id.

**Schema 15 is what the run list stops hiding, and what a client may ask it about by name.** Two things, both additive: every field 14 served is served with the same meaning and the same value, so a client written against 14 reads a 15 payload unchanged, and the API version does not move.

The run-list payload gains **`unreadable`**, an optional array beside `runs` and `next_cursor`. One entry per run root the reader refused, `{path, reason}`, carrying that root's path and the **reader's own** reason for refusing it — never a second wording of it, because a refusal restated is a second thing to keep true. It is **absent**, not empty, when nothing was refused. A run root that cannot be read used to be dropped in the read, which is how a third of a host's runs went missing with nothing saying so: a silent omission is indistinguishable from a server that has nothing to say, and an operator reading an empty list on a host that holds runs concludes nothing is running.

The run-list route also accepts **`?select=`**, a comma-separated list of run ids, answering the same row shape in the same order. On the **existing** route rather than a new one, because the ordering a row is served in is one rule and a second route would be a second copy of it to drift. A comma needs no escaping rule: a run id on this wire is already a validated bare name, so one cannot occur inside an id. What it is for is that an invalidation frame names the run that moved and refreshing that one row must cost one row — so the event stream stays an invalidation channel rather than becoming a second, disagreeing copy of run state. Three rules, each a ruling rather than a default:

- A named run that **no longer exists** is named in **`missing`**, a companion array of run ids on the same payload, beside the ordinary rows for the ones that do. Not a refusal — a run removed between the frame and the refetch is a normal race — and not a silent omission, for the reason `unreadable` exists. A named run that *is* there and will not read is reported on `unreadable` instead: those are two different facts to a caller.
- A selection **returns no cursor**. It answers exactly the runs named, and the number of ids is bounded by the same maximum a page is clamped to; a larger selection is `422 invalid_request` rather than silently truncated, because a caller that named sixty runs and was served fifty cannot tell which ten it did not learn about. Ids repeated in one selection are answered once.
- The **settled filter is not applied** to a selection. `include_settled` decides what a *page* is worth listing; a caller that names a run wants that run, and a settled row that cannot be refreshed reads as a stale view.

A selection and a page are two answers to different questions, so `?select=` sent beside `limit`, `cursor` or `include_settled` is `422 invalid_request` naming what it will not take. Resolving it instead — serving the selection and dropping the rest — would leave a caller who asked for a second page of named runs reading the first as though it were the answer.

A selection touches only the runs it names: the runs root is never listed for one, which is what makes the one-row refresh cheap.

**What a listing costs is part of this contract.** A run-list row is read from the run's own bounded summary document and never from a fold of its journal, so a row costs the same whether the run recorded ten records or ten million; a run the page does not serve costs that one fixed-size read and nothing else; and building a row, resolving anything further about a run, and reaching outside the process are done only for the rows served. Ordering by last activity needs every run's last activity, so the cost of a listing is not independent of how many runs the root holds — but it is independent of everything else, and a page of one never costs more than a page of fifty. A route about one named run opens that run and does not survey the root. An open event stream detects that nothing changed from the runs root's listing and one metadata lookup per run: on a tick where nothing moved it opens nothing and reads no bytes, and a run it does open is a run whose journal has actually grown.

#### Read-time filtering

`?filter=` on the run-detail, timeline and event-stream routes selects which events a response carries. It takes either a **named profile** or an **inline spec**, and it is resolved against the run being read.

Two profiles are defined for every run, whatever it was launched with, and they are the two the engine ships under the same names. **`planner`** is the planner's attention, and it is the engine's shipped profile of that name, read from the linked engine rather than restated — *adopted on the manager's ruling that this API carries the linked engine's filter grammar and `planner` profile, whose authority is onepipeline's `docs/contract.md` (its entry 123 in `docs/contract-divergences.md`)*: `include: [{source: "pipeline"}, {source: "vcs", significance: "milestone"}, {source: "vcs", significance: "blocker"}], exclude: [{source: "pipeline", significance: "progress"}]` — every pipeline-level event but one stamped progress, and every `vcs` milestone and blocker, with the detailed `agentgraph` activity and `vcs` progress left out. An unstamped pipeline event is in and an unstamped `vcs` event is out, because which event carries which stamp is each producer's own table: this API classifies no event's significance itself. **`detailed`** is detailed activity — the whole merged stream, all three sources — which is what an observer of a run reads; it narrows nothing, and is named rather than derived so that the two settings a viewer switches between are two profiles rather than a profile and an absence. The engine shipped that profile as `monitor` until it stopped naming an observer member at all, and ships no alias: `monitor` names no built-in profile here either, so a run whose launch defined none is answered `404 unknown_filter_profile` for it, and a run whose launch defined a profile under that word serves it as that launch's own. A run's launch config may define further names: the `filters.profiles` block a `--launch-config` file or a `--filter-profile NAME=SPEC` flag lands in, which the launch record retains as the engine's own typed block, and a retained `onepipeline start --set filters.NAME=SPEC` override, which the record keeps verbatim from the launches that predate that block — either defines profile `NAME` for that run alone and may not shadow a built-in one. A name no profile answers to is `404 unknown_filter_profile`, and the message lists the names that run does have.

The inline form is the stack's shared grammar, duplicated here per repository exactly as the envelope is: `{"include": [MATCHER, …], "exclude": [MATCHER, …]}`, where a matcher may name `source` (exact), `kind` (a glob over the wire string, where `*` stands for any run of characters including none), `phase` (exact, against the agent envelope's one reserved top-level dimension, which `onevcs` stamps on a change's records and `onepipeline` relays as stamped), the reserved label keys `run_id`, `node`, `step`, `member`, `persona` (exact), and `significance` (exact, against the word — `milestone`, `blocker` or `progress` — a producer stamped among an envelope's labels; adopted from onepipeline's contract on the same ruling). Every field a matcher names must hold; a field it does not name is not consulted; a label the envelope never stamped matches nothing, and so does a phase or a significance it never carried; a significance word the engine does not spell is `422 invalid_request`. **`exclude` wins**, and an absent or empty `include` admits everything. There is no `round` matcher — there are no rounds. A spec is validated at the trust boundary before any run is read: a matcher naming no field at all, or one whose field is empty, is `422 invalid_request` naming which list it is in, where, and what it says.

**Filtering shapes responses and never run state.** A filter is a read, and it narrows only the events a payload carries: every node status, settlement, decision, count and timing is folded from the whole journal whatever the filter said, so a reader narrowing their attention is shown the same graph in the same states as one who asked for everything. On the event stream — which invalidates rather than restating state — a filter decides which movements are worth announcing, so a run whose only new records the filter excludes does not wake that subscriber.

The browser view carries this as one affordance: a **Decisions / Detailed activity** switch in the toolbar, held in the query string as `?detail=` alongside every other selection, so a narrowed reading is bookmarkable and survives a back button. It maps to the `planner` and `detailed` profiles, which is the same distinction those two get on the CLI.

**Telemetry schema 23 preserves each observed check's remote evidence separately.**
`node_details[NODE].verification.checks` keeps its existing `state` and optional
`status`, and gains optional `conclusion`, `url`, `started_at` and `completed_at`,
copied from the latest `change-check` record for that name. Null, non-string,
empty or absent values are omitted, as are malformed URLs or RFC3339 timestamps.
Times are the producer's timestamps, never the journal observation
time. Every field schema 22 served retains its meaning and value. The browser's
Remote tab shows each check's **runtime** from these two and nothing else:
`completed_at - started_at` for a finished check, the time elapsed since
`started_at` labelled `running` while `completed_at` is absent, and nothing for a
check with no `started_at`, which is queued.

**Telemetry schema 24 carries effective run labels and resolved groups.** Rows in
`GET /api/v2/runs` and the runs nested in `GET /api/v2/projects` carry `labels`,
the engine’s opaque string-to-string map, omitted when empty, and `group`, the
engine’s resolved qualified project group, omitted when absent. Overlays written
by `onepipeline label` apply to ended and pre-label runs as well as new launches.
Resolution uses the explicit group, then the recorded copy origin, then the
launched project. `ProjectGroup.project` is that resolved group (or `null`),
and each group carries the same labelled rows as the flat listing. The recorded
`project` remains the launched project; a board copy can therefore have distinct
`project` and `group`. No other schema-23 field changes meaning.

`GET /api/v2/host` also carries optional `reading`, the SDK's `HostReading`
with its own `schema_version: 1`, unchanged: `host`, `root`, nullable
`root_error`, `free_space` (roots with role, nullable path and measured_at;
nullable free_bytes, total_bytes and error), `dispatches` (run, node,
launcher, nullable age_ms, proof held/unproven and nullable unproven reason),
`gone` (run, node, reason) and `skipped` (path, reason). The existing `rendered`
text is preserved.

Under schema 24, run detail additionally carries optional `telemetry`: the unchanged
SDK telemetry document also served as `/telemetry`'s `telemetry` field, including its
own schema_version, exact millisecond buckets, usage and counters. It describes the
whole run regardless of an event filter. Existing read API routes remain available.

Schema 24 also adds optional `launch.started_at`, the SDK's recorded launch time
unchanged, on rows and detail. Projects retain activity ordering. The browser orders
a project's runs by launch time, newest first; undated launches follow dated ones,
ordered by last activity. A late write to an older run does not select it over a
newer launch.

Schema 24 also makes a node's status the engine's word everywhere it is served.
`graph.node_status`, `node_states`, `node_gated_by`, `node_control`,
`graph.node_results[NODE].status`, the run's per-node telemetry rows, and the fold's
`node_counts` all read the engine's own `statuses()` — the word `onepipeline status`
and `results` print — so no two views of one node show different words. The
vocabulary gains **`ready`**, the engine's word for a node eligible now with nothing
dispatched, which was served as `pending` before. What the run recorded for a node is
not dropped: where the journal's settlement or the recorded `result.json` named a
status other than the engine's (`not-completed`, `improvised`, a `blocked` the graph
has since read as `skipped`) and recorded no outcome, that word is served as the
node's `outcome`. A node the graph does not carry keeps the recorded result's words.
