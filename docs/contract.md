### onepipeline-ui contract

Rust (axum) server wrapping the onepipeline SDK. Endpoints preserved so the copied frontend re-points with minimal change:

```
GET /healthz
GET /api/v2/runs                      # list w/ session attribution
GET /api/v2/runs/{run}                ?include_conversations=bool&filter=SPEC
GET /api/v2/runs/{run}/timeline       ?scope=run|node&node=ID&filter=SPEC
GET /api/v2/runs/{run}/conversations/{id}
GET /api/v2/runs/{run}/artifacts/{id}
GET /api/v2/events                    # SSE; fresh snapshot per connection; ?filter=SPEC
```

`/healthz` is the one response that is not enveloped — liveness must answer without reading run storage, so it has no schema version to read one from — and it carries two fields: `status`, whose only value is `ok`, and `onepipeline_version`, the `onepipeline` release this binary links, read from that crate's own `VERSION` rather than restated here. A host that pins the engine writing a run store and separately pins this reader of it has nothing else to prove the two are the same release, so the reader says which one it is rather than leaving it assumed.

Payloads keep the telemetry schema-version discipline and serve schema 13 including `dispatch_id` — schema 10 was where `dispatch_id` landed, and 11 is that discipline exercised: an unmeasured timing is served `null` rather than `0`, so a lane nothing measured can no longer read as a measured zero. Anything the API computes that is presentation-worthy lands in the onepipeline SDK/CLI first: the agent reading the CLI must have the same or better visibility than the human in the UI.

Schema 12 answers, per node in flight, whether the run has a turn it can address for it — the precondition a planner needs before choosing between correcting a node and cancelling it. `node_control` carries one entry for every node recorded as `running` and for no other, and each entry is `{addressable, member?, reason?}`, with `reason` present exactly when `addressable` is false. A node whose turn this run cannot address reads as `addressable: false` carrying the reason — never as an error and never as an absent value — and where an interrupt has already been attempted the reason is the producing library's own words for what it found.

`addressable` means **this run has a turn it can address for that node** — the engine's own precondition for delivering a note into a running turn — read from whether a member is in a turn and from the outcome of every interrupt already attempted, which is published for every attempt whether or not it landed. It is not a claim that the harness will accept a redirection. No published component exposes an authoritative *current-turn* control state outside the process running the turn: onejudge reports `control` only on the finished run, the live provider accessor is in-process only, `oneagentgraph`'s spawn-time record is provisional for every member whatever its harness, and the control protocol's only verb is `interrupt`, which costs the turn. A previous dispatch's report is not a substitute and is never read as one — `provider.control` is asked for per run and reset for the next. `src/AGENTS.md` records each closed route and the upstream change that opens one.

**Schema 13 is the removal of rounds.** Execution in the onepipeline SDK is continuous and dependency-driven: a node — and each step within a lifecycle node — dispatches the moment its dependencies settle `done`, nothing batches them, and the envelope's `round` label is deprecated and stamped by nothing. So the payload's `rounds` array is replaced by one **`graph`** object describing the run's whole state, and no `round` survives anywhere in a response. A client reading 12 must not read a 13 payload: the array it indexed is gone, not renamed. `graph` is `{run_id, plan, node_states, node_status, node_gated_by, node_control, node_results, decisions, attestations, result, last_seq}` — one desired graph with every committed live edit applied, and one recorded `result`, which the SDK rewrites whenever a driver closes out.

`decisions` is what replaces a round's own account of why a run is not moving. The only thing that pauses anything is a **decision point**, and it pauses only the subtree that depends on it — a ready `kind: human` node's attestation, or a blocking surface nobody has answered — while independent branches proceed. Each entry is `{id, kind, unblocks}`, mirroring the SDK's own `decision-pending`, and it is absent from the list again once `decision-cleared` releases the subtree. `phase` names a continuous phase — `starting`, `dispatching`, `deciding`, `surfacing`, `waiting`, `settled`, `finished` — rather than a position in a batch, and `node-ready` is the kind that reports a node became eligible to dispatch. Plan schema 2 retired `done_when`, so no plan task carries one: a node's bar is the `## Acceptance criteria` section of its own task prose, which is what the judge is handed.

Timeline schema 4 carries the redirection itself. An event produced by a `turn-interrupted` or by an `edit-committed` that added context to a node carries `redirection` — `{delivered, member?, input_bytes?, reason?, delivery?, node_id?}` — so a turn whose behaviour changed mid-flight shows the moment the planner changed it, and whether the note went into the running turn (`live`) or onto the node's next dispatch (`deferred`). An `edit-committed` additionally carries the `author` that submitted it, `planner` or `monitor`: the run enforces a per-author op allowlist, so an observer's self-applied fix and the planner's own decision are two different facts about one graph.

**Timeline schema 5 is continuous too.** The run itself is the single root span (`kind: "run"`), not one span per round; no span or event carries a `round`; and every span id is keyed by what it identifies — `run.RUN`, `node.ID`, `dispatch.SESSION`, `publication.ID`, `verification.ID.ARTIFACT`, `rollup.ID.…`, `human-wait.ID` — rather than by a round number. A node has one span however many times it was dispatched: the SDK re-asks a dispatch that produced nothing and records each attempt as its own `node-dispatched`, and every attempt is the same node's same work.

#### Read-time filtering

`?filter=` on the run-detail, timeline and event-stream routes selects which events a response carries. It takes either a **named profile** or an **inline spec**, and it is resolved against the run being read.

Two profiles are defined for every run, whatever it was launched with. **`planner`** is the decisions-level view: onepipeline's own event vocabulary is a closed set and it is exactly the decision vocabulary, so the profile is `include: [{source: "pipeline"}]`. **`monitor`** is detailed activity — the whole merged stream, all three sources — which is what the monitor persona's own contract says it reads; it narrows nothing, and is named rather than derived so that the two settings a viewer switches between are two profiles rather than a profile and an absence. A run's launch config may define further names: a retained `onepipeline start --set filters.NAME=SPEC` override, which the launch record keeps verbatim, defines profile `NAME` for that run alone and may not shadow a built-in one. A name no profile answers to is `404 unknown_filter_profile`, and the message lists the names that run does have.

The inline form is the stack's shared grammar, duplicated here per repository exactly as the envelope is: `{"include": [MATCHER, …], "exclude": [MATCHER, …]}`, where a matcher may name `source` (exact), `kind` (a glob over the wire string, where `*` stands for any run of characters including none), and the reserved label keys `run_id`, `node`, `step`, `member`, `persona` (exact). Every field a matcher names must hold; a field it does not name is not consulted; a label the envelope never stamped matches nothing. **`exclude` wins**, and an absent or empty `include` admits everything. There is no `round` matcher — there are no rounds. A spec is validated at the trust boundary before any run is read: a matcher naming no field at all, or one whose field is empty, is `422 invalid_request` naming which list it is in, where, and what it says.

**Filtering shapes responses and never run state.** The API is read-only, and a filter narrows only the events a payload carries: every node status, settlement, decision, count and timing is folded from the whole journal whatever the filter said, so a reader narrowing their attention is shown the same graph in the same states as one who asked for everything. On the event stream — which invalidates rather than restating state — a filter decides which movements are worth announcing, so a run whose only new records the filter excludes does not wake that subscriber.

The browser view carries this as one affordance: a **Decisions / Detailed activity** switch in the toolbar, held in the query string as `?detail=` alongside every other selection, so a narrowed reading is bookmarkable and survives a back button. It maps to the `planner` and `monitor` profiles, which is the same distinction those two get on the CLI.
